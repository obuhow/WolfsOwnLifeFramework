# 0005 — Слоистая архитектура API (тонкий MVCS + точечные порты)

- Статус: **Принято** (2026-08-26, релиз 0.9)
- Контекст: WOLF 0.9, миграция `wolf-api` со смешанных контроллеров (где бизнес-логика
  и инъекция `Repository` живут в контроллере) на согласованную слоистую архитектуру.
- Связано: `.scratch/wayfinder-release-0.9-layered-arch/map.md` (вариант D — гибрид).

## Проблема

На замере релиза 0.9: 39 контроллеров, из них 36 инжектят `Repository` напрямую и несут
бизнес-логику; `Request`/`Response` живут как вложенные `@Data`-классы в контроллерах;
нет единого паттерна «куда класть слой». Через 39 фич-тикетов нужен **один воспроизводимый
образец**, чтобы параллельные агенты не порождали вариации.

## Решение

Базовый паттерн — **тонкий MVCS**:

```
Controller  →  Service  →  Repository
(HTTP, валидация,    (бизнес-логика,   (JPA)
 @Transactional)      @Transactional)
```

Каждый контроллер фичи:

1. **Не инжектит `Repository`** — единственная зависимость уровня данных идёт через `Service`.
2. Делает только HTTP-обязанности: маршрутизация, `@Valid`, чтение пути/параметров,
   маппинг тела запроса в DTO, обёртка ответа в `ResponseEntity`.
3. Получает текущего пользователя **не из `SecurityContextHolder` и не из `Authentication`**
   напрямую, а делегирует: контроллер передаёт строку `authentication.getName()` (или сам
   `Authentication`) в `Service`, а `Service` резолвит `User` через `UserRepository`.
   Обоснование: контроллер не должен владеть `UserRepository` (нарушение п.1), а сервис —
   естественное место для резолва владельца ресурса. Образец уже есть в коде:
   `MorningDigestController` → `MorningDigestService.build(authentication.getName())`.

`Service`:

- Помечается `@Service` + `@RequiredArgsConstructor` (Lombok).
- Несёт `@Transactional` / `@Transactional(readOnly = true)` на методах (переезжает
  из контроллера).
- Резолвит `User`: `userRepository.findByUsername(name).orElseThrow(...)`.
- Бросает те же доменные/валидационные исключения, что раньше бросал контроллер, —
  `GlobalExceptionHandler` ловит их по типу, поэтому HTTP-контракт не меняется.

### DTO

- Java **records** в подпакете `dto/` каждой фичи: `ru.wolf.api.<feature>.dto`.
- Naming: запросы `Create<X>Request`, `Update<X>Request`, `Promote<X>Request`;
  ответы `<X>Response`; специфичные ответы действий `<X><Action>Response`
  (например, `PromoteResponse`).
- Bean-валидация (`@NotBlank`, `@Size`, `@NotNull`) — на полях record'а, как было
  на `@Data`-классах. Record с валидацией: поля final + аннотации работают при `@Valid`.
- Маппинг — **ручной**, статический фабричный метод **на самом record**:
  `public static IdeaResponse from(Idea idea)`. Без MapStruct, без отдельного `XxxMapper`.
- `from` строит flat-ответ: для `@ManyToOne` связей кладёт `id`/`title` соседа, а не объект,
  чтобы не тянуть граф сущностей в JSON и не словить lazy-инициализацию вне транзакции.

### Порты и адаптеры (точечно)

Только где уже есть или явно предвидится второй адаптер (правило «два адаптера — реальный
шов»):

- Интерфейс `XxxPort` в пакете фичи.
- Реализации-адаптеры называются по роли: `JpaXxxAdapter`, `HttpXxxAdapter`, `FakeXxxAdapter`.
- Образец: `note/assistant` (`NotesAssistant` — порт; `FakeNotesAssistant`/`HttpNotesAssistant`).

### Доменные исключения

`IdeaAlreadyPromotedException`, `DuplicateGoalPriorityException` и т.п. **остаются рядом с
моделью** (в пакете фичи), не переносятся. `GlobalExceptionHandler` в `api/common/` ловит их
по типу → статус код сохраняется независимо от того, брошены они из контроллера или сервиса.

### Осознанные исключения из «не трогать тесты»

`*ApiIT` — это реально чёрный ящик (HTTP), и их логика не меняется. НО если DTO был
вложенным типом контроллера (`IdeaController.IdeaResponse`) и переезжает в `dto/`,
все ссылки на FQN типа в любых `*ApiIT` (включая соседние фичи, например
`MorningDigestApiIT` ссылается на `IdeaController.CreateIdeaRequest`) надо поправить
**только по квалификатору** (`ru.wolf.api.idea.dto.CreateIdeaRequest`), не меняя ни одной
строки проверяемого поведения. Это механическая правка, не меняющая контракт; она
допускается DoD п.4 («проходят без правок их кода» интерпретируется как «без правок логики»).

Дополнительно: исходные вложенные классы были Lombok-`@Data`, поэтому тесты звали
JavaBean-геттеры (`idea.getId()`). Переезд на **records** меняет accessor-форму на
`idea.id()` — это тоже чисто механическая правка (record-accessor вместо getter),
проверяемое поведение не меняется. Референс: `IdeaApiIT` в тикете 01 поправлен именно
так (FQN + `getId()`→`id()`), и проходит 5/5.

## Исключения из миграции

`HealthController` и `WolfApiApplication` — вне контура (нет БД/бизнес-логики).
`Ports & Adapters` — только для `note/assistant` и `datasync` (где два адаптера),
остальное — обычный `Service`.

## Последствия

- `+` единообразие: любой агент копирует один образец (`Idea`) на всю фичу.
- `+` контроллеры становятся узкими (HTTP-only), бизнес-логика тестируема на сервисе.
- `-` в первом тикете правятся FQN DTO в затронутых `*ApiIT` (см. выше) — единственный
  неизбежный шум.
- Референсная реализация паттерна: `ru.wolf.api.idea` (тикет 01 релиза 0.9).
