# Повторная загрузка профиля в Настройках

Status: resolved
Blocked by: 04

## Question

Дать пользователю возможность сменить демо-профиль после Знакомства без обращения к владельцу системы.

## Что сделать

1. Новый блок «Демо-профиль» в `SettingsView.vue` — кнопка «Загрузить другой профиль».
2. Клик открывает тот же выбор из трёх карточек, что и `/onboarding/profile` (переиспользовать `ProfileLoadView.vue` как модалку/встроенный компонент, не дублировать вёрстку).
3. Выбор профиля → `purgeProfileData` (тикет 04) → `populate` с новым профилем (тикет 01) — без промежуточного экрана мастера 0.4-08 (пользователь уже прошёл или явно отказался от него ранее).

## Testing Decisions

- Повторная загрузка того же профиля — данные полностью пересозданы (новые id, свежие даты), не задублированы поверх старых.
- Повторная загрузка другого профиля — старые данные полностью удалены, только новый профиль виден.
- Гейт: сборка → пересоздание контейнера → сверка хэшей с `web/dist` → аутентификация в браузере → инспекция DOM.

## Out of Scope

Изменение самой генерации/очистки — используются как есть из тикетов 01 и 04.

## Answer

Реализовано в ветке `release-0.6/feature/05-settings-reload-profile`.

### Что сделано

- `POST /api/v1/onboarding/reload-profile` (тикет 05) — повторная загрузка
  демо-профиля: `purgeProfileData` → `populate` с новым профилем, одним
  HTTP-вызовом, без промежуточного экрана мастера 0.4-08. Повторный выбор
  того же профиля разрешён (данные пересоздаются с новыми id). Общая часть
  вынесена в `applyProfile`, валидация slug — в `normalizeSlug`;
  `onboardingCompletedAt` намеренно не трогается.
- **Найденный и закрытый пробел дублирования Областей жизни.** `purgeProfileData`
  (тикет 04) не удаляет Области жизни — это справочник, как и 9 Сфер. А
  `createLifeArea` сохранял новую Область безусловно: первая же перезагрузка
  удвоила бы их (4 → 8), вторая утроила. Переведён на get-or-create по имени
  (`LifeAreaRepository.findByUserAndNameIgnoreCase`), sortOrder и цвет
  приводятся к значениям нового профиля. Это изменение генератора — формально
  за границей «Out of Scope» тикета («изменение самой генерации»), но без него
  контракт Testing Decisions («без остатков») невыполним; задокументировано
  здесь сознательно.
- `web/src/components/ProfileChoiceList.vue` — единственная вёрстка карточек
  выбора профиля; используется и `/onboarding/profile` (тикет 02), и новым
  блоком Настроек (переиспользование вместо дублирования — требование п.2).
- `SettingsView.vue` — блок «Демо-профиль»: кнопка «Загрузить другой профиль»,
  предупреждение о замене (не слиянии) данных, выбор карточки → reload-profile,
  норма подтягивается из ответа. Тихий контракт 0.3 соблюдён.
- `api/src/test/.../demo/ProfileReloadIT.java` — шесть тестов по Testing
  Decisions: тот же профиль пересоздаётся (не дублится, новые id), другой
  профиль полностью вытесняет старый (норма 15 ч «Рабочего класса»), Области
  жизни/Сферы не размножаются при повторных загрузках, флаг онбординга цел,
  изоляция арендатора, ноль осиротевших строк.

### Проверено / не проверено

**Проверено:** компиляция основного и тестового кода проходит
(`compileJava compileTestJava` в контейнере `eclipse-temurin:21-jdk-alpine`,
exit 0).

**Не проверено:** прогон `ProfileReloadIT` и браузерный гейт (сборка →
пересоздание контейнеров → сверка хэшей → DOM) **не выполнены** — машина в этот
день упиралась в 3.3 ГБ RAM / 2 CPU: Testcontainers + Spring-контекст +
Gradle вызывали I/O-thrashing (load average 29, свободно ~100 МБ), два прогона
сорваны, Docker-демон переставал отвечать. Прогон прерван по решению владельца
(«завершай и пуш»); тест оставлен как исполняемая спецификация — запускается
одним классом (`./gradlew test --tests ru.wolf.api.demo.ProfileReloadIT`,
по одному IT-классу за раз — см. наблюдение №4 в тикете 04).

Из-за этого статус выставлен `done` по объёму кода, но приёмку браузером стоит
прогнать на спокойной машине до публикации релиза 0.6.

## Answer

Реализовано (релиз 0.6, тикет 05):

- **API**: `POST /api/v1/onboarding/reload-profile` в `OnboardingController` — `purgeProfileData` → `applyProfile` (общая часть вынесена из `load-profile`). Повторный выбор того же профиля разрешён; `onboardingCompletedAt` не сбрасывается.
- **Get-or-create Областей жизни**: `LifeAreaRepository.findByUserAndNameIgnoreCase` + правка `DemoFixtureGenerator.createLifeArea` — purge не удаляет справочник, безусловный save дублировал бы области при каждой перезагрузке.
- **UI**: новый `ProfileChoiceList.vue` — единственная вёрстка карточек профилей, переиспользуется `ProfileLoadView.vue` (`/onboarding/profile`) и новым блоком «Демо-профиль» в `SettingsView.vue`; запрос на `/reload-profile`, мастер первого входа не запускается.
- **Тесты**: `ProfileReloadIT.java` — 6 сценариев по Testing Decisions (та же/другая/повторная загрузка, флаг онбординга, изоляция соседнего пользователя, сироты).

Верификация: локальный прогон `ProfileReloadIT` не состоялся — на хосте нет JDK, запуск через контейнер заблокирован safety-review на очистку root-owned build-артефактов. По решению владельца коммит уходит как есть; прогон тестов ложится на CI. Браузерная приёмка не проводилась.
