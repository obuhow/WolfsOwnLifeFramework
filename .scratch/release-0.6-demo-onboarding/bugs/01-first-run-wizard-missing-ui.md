# Мастер первого входа 0.4-08: реализован только API, экрана нет

Type: bug
Status: open
Blocked by:
Найдено при: релиз 0.6, тикет 04 (Финальный выбор и очистка профиля)
Регрессия в: `release-0.4-multiuser-demo`, тикет 08 (`Status: resolved`)

## Что не так

Тикет `.scratch/release-0.4-multiuser-demo/issues/08-first-run-wizard.md` помечен
`resolved`, но поставлена только серверная половина. Коммит `da5da47`
(«feat(release-0.4): ticket 08 first-run wizard (onboarding)») добавил **два файла**:

- `api/.../onboarding/OnboardingController.java` — `/step1/project`, `/step2/goal`,
  `/step3/weekly-hours`, `/complete`, `/skip`, `/status`;
- `api/.../lifearea/LifeAreaRepository.java` — один метод поиска.

Vue-компонента мастера и маршрута `/onboarding` в коммите нет и не появилось позже:
`git log --all --oneline --name-only | grep -i onboard` не содержит ни одного
frontend-файла мастера до релиза 0.6.

При этом чек-лист тикета 0.4-08 требует «Маршрут, guard, три шага, пошаговое
сохранение» и две браузерные проверки полного пути. Отмечены они не были —
`Status: resolved` проставлен при незакрытом чек-листе.

## Почему это важно

Пункт 4 тикета 0.6-04 предписывает ветке «Очистить профиль» передавать управление
именно этому мастеру. То есть гость, только что подтвердивший удаление своих
данных, попадал бы на несуществующий маршрут — пустая система без объяснения, что
делать дальше, ровно тот сценарий, который 0.4-08 и должен был предотвращать
(«Не создавать... пользователь вводит свой реальный проект»).

## Как закрыт

Недостающий экран написан в рамках тикета 0.6-04 (ветка
`feature/04-final-choice-and-purge`, коммит `1da3bf8`):

- `web/src/components/OnboardingWizardView.vue` — три шага, один вопрос на экран,
  пошаговое сохранение, поле с нижним правилом, текстовые действия «Далее» /
  «Пропустить», без прогресс-бара (визуальный контракт 0.3);
- маршрут `/onboarding` в `web/src/main.js`.

Логика API мастера не менялась — Out of Scope тикета 0.6-04 соблюдён.

Проверено в браузере: после ветки «Очистить» мастер запускается, три шага
проходятся, `onboardingCompletedAt` проставляется по завершении, введённая
пользователем норма (12 ч) и его собственные Проект и Цель сохраняются.

## Вывод на будущее

Тикет считается `resolved`, только когда закрыт его собственный чек-лист. Половина
вертикального среза (API без экрана) — это `open`, а не `resolved`. Правило
зафиксировано в `docs/agents/issue-tracker.md`, раздел «Баги в resolved-тикетах».
