# Разбор образца расписания — Расписание.xlsx

Дата: 2026-09-03
Файл: `sample/Расписание.xlsx` (реальные данные obuhov, ~482 КБ, извлечён через read_file)
Цель: понять структуру и решить — чинить XLSX-импорт WOLF / писать конвертер / агент-LLM.

## Структура файла (подтверждена по извлечённому тексту)

- **Один лист на неделю**: `1-7 июня`, `8-14 июня`, `15-21 июня`, `22-28 июня`, `29-5 июля`, …
  Структура **одинаковая от листа к листу** (подтвердил владелец).
- **Строка 1**: даты-серийники Excel (`46174 46175 … 46180` = 7 дней недели) + «Задачи на неделю».
- **Строка 2**: заголовки дней `Понедельник … Воскресенье`.
- **Колонки A,B,C**: служебное время — час (A), минута (B), время как дробь Excel (C:
  `0.2916…` = 07:00, шаг +15 мин).
- **Колонки D–J (4–10)**: 7 дней недели; ячейка = текст активности (ФАКТ, что реально делал).
- **Нижний блок «Факт»**: посчитанные часы по категориям (Java, QA, Гитара, Финансы …) за
  каждый день — уже готовая агрегированная динамика (владелец считал вручную).

## Классификация: НЕ «свободный стиль», а чужая-но-регулярная сетка

Детерминированный парсер под эту структуру надёжнее и дешевле LLM-агента-конвертера
(принцип WOLF «числа считает код»). LLM здесь избыточен и рискован (тысячи ячеек).

## Решение владельца по семантике

- Каждая ячейка = **ФАКТ** → грузить как Записи времени со статусом **DONE**.
- Маппинг активностей → Дела: **«по неизвестным, система спрашивает»** — ровно механизм,
  который в XLSX-импорте WOLF УЖЕ есть (`activity_mapping` + `xlsx_import_question`).

## Почему существующий XlsxImportService НЕ берёт этот файл (4 дефекта)

Референс: `api/.../importxlsx/XlsxImportService.java:60-90`, миграция `V24__xlsx_import.sql`.

1. **Дата недели из имени листа** (`parseWeek`, `:114`): regex ищет `YYYY-MM-DD` в названии.
   Имена листов — `«1-7 июня»` и т.п., **даты нет ни в одном** → у всех недель молчаливый
   дефолт `LocalDate.of(2026,4,6)` → все недели легли бы на одну дату. Настоящие даты — в
   **строке 1 как серийники** (`46174`), их импорт не читает.
2. **Смещение слотов** (`:65-66`): импорт считает строка 0 = заголовок, строка 1 → 00:00,
   +15 мин по номеру строки. У файла шапка в 2 строках и первый слот — **07:00 из колонки C**
   (`0.2916…`), не полночь → все активности встанут не на своё время.
3. **Колонки дней** (`:67-68`): импорт читает колонки 0–6 (A–G). В файле дни — в **D–J (3–9)**,
   а A–C заняты временем → импорт прочитает время/пустоту вместо активностей.
4. **Диапазон и мусор**: день начинается 07:00 (не 00:00); внизу листа блок «Факт» (часы по
   категориям) импорт примет за активности и наплодит ложные Записи.

## Вывод / рекомендация

- Механизм на 80% готов (маппинг с обучением, вопросы по неизвестным, дедуп по хешу файла,
  статусы) — это **починка парсинга сетки под конкретный формат**, а не стройка с нуля.
- Путь: расширить `XlsxImportService` (или отдельный адаптер формата) так, чтобы читать
  даты из строки серийников, время из колонки C, дни из D–J, игнорировать блок «Факт»,
  грузить как DONE. Маппинг/вопросы переиспользовать как есть.
- LLM-агент-конвертер для ЭТОГО файла не нужен. Он остаётся в запасе для действительно
  свободных таблиц (если такие появятся) — но не тут.

## Открытые технические вопросы (в тикет)

- Excel-серийник → дата: 1900-датировка Excel (серийник 46174 → нужно проверить точную
  дату; учесть баг Excel 1900-leap). Считать детерминированно в коде.
- Слитные подряд ячейки одной активности (напр. `Java` 8 строк) — исходная гипотеза спайка
  предполагала 8 отдельных 15-минутных Записей. Это решение **заменено владельцем**: в
  финальном импорте непрерывный участок одного Дела хранится одной Записью времени с
  интервалом `[startAt, endAt)`; подробности и тесты — в тикете 07.
- Нормализация вариаций («в спортзал»/«Спортзал», «Английский клуб»/«Клуб английского») —
  маппинг это стерпит (обе строки → одно Дело через две записи activity_mapping), но стоит
  отметить владельцу.
