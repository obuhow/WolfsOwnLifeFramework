## Problem Statement

У владельца ~полгода реального факта (что делал по 15 минутам) лежит в Excel —
`Расписание.xlsx`: недельная сетка, 11 листов (1 июня – 16 авг 2026), 1943 заполненные
ячейки, 67 уникальных активностей. В WOLF этих данных нет — из-за чего «динамика за полгода»
для агента-планировщика (направление `agent-chat-planner`) собирается по пустоте.

В WOLF **уже есть** XLSX-импорт расписания (`XlsxImportService`, `/api/v1/import/xlsx`) с
нужным механизмом: маппинг «активность → Дело» с обучением (`activity_mapping`), вопросы по
неизвестным активностям (`xlsx_import_question`), дедуп по хешу файла, статусы
PLANNED/DONE/UNKNOWN. Но он **не читает конкретно этот формат** — спайк подтвердил 4 дефекта
(`sample/ANALYSIS.md`):

1. дату недели берёт из **имени листа** (regex `YYYY-MM-DD`) — у файла имена «1-7 июня» →
   молчаливый дефолт, все недели на одну дату; настоящие даты — в строке серийников;
2. слоты считает от 00:00 при шапке в 1 строку — у файла шапка 2 строки, день с 07:00;
3. дни в колонках A–G — у файла в **D–J**, причём **колонка D = воскресенье** (сдвиг!);
4. берёт все строки — внизу листа блок «Факт» (часы по категориям) даст ложные Записи.

## Solution

Расширить `XlsxImportService` (feature `importxlsx`) под реальный формат сетки, добавив слой
предпросмотра и осознанное разрешение конфликтов. LLM-конвертер НЕ вводится — формат
регулярный, парсинг детерминированный (принцип WOLF «числа считает код»). Ключевые решения:

- **Парсер формата (И-A, Т-2):** даты из строки серийников Excel (row 1, компенсация бага
  1900-високосного), дни **Вс–Сб** (колонка D = воскресенье), время из колонки C (дробь),
  активности из D–J, блок «Факт» игнорируется.
- **Хранение (И-D):** каждая заполненная ячейка → отдельная **15-мин Запись времени `DONE`**
  (модель WOLF: одна ячейка = одна Запись; записи произвольной длительности нет). «Склейка в
  интервалы» — только визуально в WeekView (О-1), не в хранении.
- **Классы активностей (И-A/B):** поддерживающие (Сон, Еда, В дороге, Питание, Обед…) →
  тоже **Дела**, но с пометкой «поддерживающее» (новый флаг, О-2); «Рутина» — способ
  сгруппировать в отображении, не отдельная сущность. «Сон» переиспользует существующее
  Дело (механизм «Ночные часы»), без дубля (Т-1).
- **Пустые/«Неизвестно» (И-C):** ничего не создаём; «пусто = неизвестно» — трактовка
  агента/UI, не материализация UNKNOWN-записей.
- **Нормализация (И-E):** тривиальная (пробелы, регистр «Сон»/«сон») — авто; смысловая
  («в спортзал»→«Спортзал») — через маппинг с подтверждением (не молча).
- **Часовой пояс (И-F):** время из Excel = локальное время пользователя (07:00 → `startAt`
  дата T07:00), без UTC-конверсий (WOLF хранит `LocalDateTime`).
- **Preview → apply (И-I):** разобрать файл без записи → сводка (недели, ячейки, новые/
  известные активности, число конфликтов) → явное «Применить». Слой поверх текущего
  «пишет сразу».
- **Конфликты (И-G/H):** конфликт = ячейка уже занята любой Записью; при apply — **сводка +
  один выбор на весь импорт**: пропустить все / перезаписать все / отменить.
- **Точка входа (И-J):** существующая страница `/import/xlsx` (`XlsxImportView`).

Архитектура — слои release 0.9 (тонкий контроллер, сервис, DTO-records; см. `AGENTS.md`).
Существующие `activity_mapping`/`xlsx_import_question` переиспользуются, не переписываются.

## Совместимость с существующим XLSX-импортом

`XlsxImportService` сейчас: пишет сразу, дни A–G, дата из имени листа, слоты от 00:00,
молчаливый `continue` на занятой ячейке. Тикеты 01–03 меняют это поведение. Решить в тикетах:
- поддержать оба формата (старый + новый) или заменить парсер под фактический формат владельца
  (в репозитории нет других известных XLSX-форматов — вероятно, замена, но зафиксировать);
- `ImportResponse` дополняется полями preview/конфликтов (обратная совместимость API).

## Проверочный факт (обновлено по итогам тикета 01)

`spike/xlsx_spike_parse.py` (чистая stdlib, без openpyxl) читал реальный файл и дал
11 недель, 1943 записи, 67 активностей. **Эти числа и часть выводов спайка оказались
неверны** — вскрылось при реализации тикета 01 прогоном прод-парсера (Apache POI) на том же
файле. Заведены `bugs/01-03`:

| Баг | Что было заявлено спайком | Как на самом деле |
|---|---|---|
| `bugs/01` | «колонка D = воскресенье, дни Вс–Сб» | D = **понедельник**; спайк декодировал серийник на сутки назад. Подписи строки 2 файла подтверждают на всех 11 листах |
| `bugs/02` | — (не замечено) | даты E–J и **все** ячейки времени — формулы; POI с проверкой `NUMERIC` даёт **ноль** ячеек. Спайк читал сырой XML, где кеш формулы неотличим от числа |
| `bugs/03` | «время — C, дни — D–J» как свойство файла | верно лишь для 9 листов; последние два сдвинуты на 2 колонки влево (время A, дни B–H) → мусорная активность «0» и потеря двух недель |

**Действующие числа (прод-парсер, после исправлений): 11 недель, 2117 ячеек, 78 уникальных
активностей, 2026-06-01 – 2026-08-16.** Дополнительно найден маркер пустоты «-/-»
(202 ячейки), не встречавшийся спайку, — пропускается наравне с «Неизвестно» (И-C).

Прод-парсер тикета 01 реализован **отдельным классом** `XlsxScheduleGridParser` (не правкой
инлайн-разбора в `XlsxImportService`): он возвращает промежуточную модель `ScheduleCell`
и ничего не пишет в БД — её переиспользует preview-слой тикета 02.

## Версия

Функциональный прирост (импорт нового формата + preview). Минорный бамп версии — в финальном
мердже релиза, куда войдёт фича (синхронно `web/package.json` + `api/build.gradle`, как в
1.0/1.1/1.2). Отдельным тикетом не заводится.

## Out of Scope (MVP)

- Материализация `UNKNOWN` на пустые ячейки (И-C1, вариант «б») — только если понадобится.
- Поячеечное/погруппное разрешение конфликтов (в2/в3) — сейчас сводка + один выбор.
- LLM-конвертер действительно свободных таблиц (этот файл регулярный, не нужен).
- Отдельная сущность Рутина с недельной квотой из импорта (И-B: пока Дела с пометкой).
- Хранение Записи произвольной длительности (модель WOLF не меняется — N×15 мин).
