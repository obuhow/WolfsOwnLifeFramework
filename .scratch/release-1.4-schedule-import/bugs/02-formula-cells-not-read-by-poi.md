# Б-2 — Даты и время в файле записаны формулами: проверка `getCellType() == NUMERIC` даёт ноль ячеек

Type: bug
Status: resolved
Найдено при: release-1.4 (импорт «Расписание.xlsx»), реализация тикета 01 — первый прогон
прод-парсера на реальном файле вернул 0 ячеек при 11 распознанных неделях.
Регрессия в: не регрессия — **слепое пятно артефакта разведки**. `spike/xlsx_spike_parse.py`
читает сырой XML (`zipfile` + `ElementTree`), где закешированное значение формулы `<v>`
неотличимо от литерального числа, поэтому спайк этой разницы не видел и в
`spike/RESULT.md` / `spec.md` / `issues/01` о ней ничего нет.

## Симптом

Прод-парсер на Apache POI (как предписывает тикет 01: «Реализация на Apache POI внутри
feature `importxlsx`») **молча возвращает пустой результат** на файле, который спайк читает
успешно:

```
=== ПРОД-ПАРСЕР на реальном файле ===
Недель (листов с датами): 9
Ячеек-активностей:        0
Уникальных активностей:   0
```

Опаснее всего именно тишина: файл «прочитан», ошибки нет, импортировать нечего.

## Доказательство расхождения

Диагностика POI по листу «1-7 июня» (типы ячеек, как их видит POI):

```
row 0: [3:NUMERIC=46174.0] [4:FORMULA] [5:FORMULA] [6:FORMULA] [7:FORMULA] [8:FORMULA] [9:FORMULA]
row 1: [3:STRING=Понедельник] [4:STRING=Вторник] ... [9:STRING=Воскресенье]
row 3: [0:STRING=0] [1:STRING=0] [2:FORMULA]
row 4: [0:STRING=0] [1:STRING=15] [2:FORMULA]
row 7: [0:FORMULA] [1:STRING=0] [2:FORMULA] [3:STRING=Сон] ...
```

То есть:

- в строке дат **литеральное число только в колонке D** (`46174`), остальные шесть дней —
  формулы вида `=D1+1`;
- в колонке времени (C) **формула в каждой без исключения строке-слоте**.

Прямая проверка `cell.getCellType() != CellType.NUMERIC` отбрасывает и то, и другое: шесть
дней из семи теряют дату, а `slotTime()` не признаёт ни одной строки слотом → ни одна ячейка
активности не собирается. Сравнение с сырым XML того же листа показывает, почему спайк был
слеп: там у формульной ячейки есть и `<f>`, и `<v>` с готовым значением, и спайк читал `<v>`.

## Как закрыт

Тикет 01, ветка `release-1.4/feature/01-grid-format-parser`, коммит `df3d472`.

- введён `XlsxScheduleGridParser.isNumeric(Cell)`, который для `CellType.FORMULA` смотрит
  `getCachedFormulaResultType()`, и применяется в обеих точках чтения чисел — строке дат и
  колонке времени;
- регресс-тест `reads_dates_and_times_written_as_formulas` строит синтетический лист ровно в
  боевой форме (D1 литерал, E1..J1 = `=D1+n`, время = `TIME(7,0,0)`) и требует, чтобы даты и
  время разобрались;
- после правки на реальном файле стало 11 недель и непустой набор ячеек.

## Замечание на будущее (важнее самого бага)

Спайк на сыром XML и прод-код на POI **видят файл по-разному**. Любая следующая находка
спайка — тоже гипотеза, а не факт для прод-парсера, пока не проверена через POI. Здесь это
уже дало два независимых расхождения: Б-2 (формулы) и Б-3 (раскладка листов), плюс Б-1
(арифметика дат). Рекомендация к тикетам 02–06: сверять поведение на реальном файле
прод-кодом, а не доверять числам из `spike/RESULT.md`.
