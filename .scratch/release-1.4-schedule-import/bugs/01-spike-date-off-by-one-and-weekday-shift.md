# Б-1 — Спайк декодировал даты на сутки назад → ложный вывод «колонка D = воскресенье»

Type: bug
Status: resolved
Найдено при: release-1.4 (импорт «Расписание.xlsx»), реализация тикета 01 — прогон
прод-парсера на реальном файле и сверка с подписями дней внутри самого файла.
Регрессия в: не регрессия кода — **дефект артефакта разведки**
(`spike/xlsx_spike_parse.py`, `spike/RESULT.md`, находки 1 и 3), на который опирались
`spec.md` и `issues/01-grid-format-parser.md`. Боевого кода дефект не достиг: пойман до
записи в БД.

## Симптом

Спайк объявил (`spike/RESULT.md`, находка 1):

> **Дни недели сдвинуты на 1**: колонка D = **воскресенье** (не понедельник). Лист
> «1-7 июня»: D1=2026-05-31 (Вс) … J1=2026-06-06 (Сб). Импорт обязан это учитывать.

Это утверждение неверно. Колонка D — **понедельник**, D1 листа «1-7 июня» = **2026-06-01**.
Если бы прод-парсер «учёл» заявленный сдвиг, **все импортированные Записи времени
оказались бы сдвинуты на сутки** — то есть полгода факта легли бы не на те дни.

## Доказательство расхождения

**1. Файл сам подписывает дни — строка 2 (r=2), лист «1-7 июня»:**

```
D2 = Понедельник   E2 = Вторник   F2 = Среда   G2 = Четверг
H2 = Пятница       I2 = Суббота   J2 = Воскресенье
```

Над этими подписями в строке 1 стоит `D1 = 46174`. Значит серийник 46174 обязан
декодироваться в понедельник.

**2. Арифметика двух формул:**

| Формула | 46174 → | День недели | Совпадает с подписью D2? |
|---|---|---|---|
| Спайк (`date(1899,12,30) + (serial−1)` при serial ≥ 60) | 2026-05-31 | воскресенье | ❌ нет |
| Стандартная Excel (`date(1899,12,30) + serial`) | 2026-06-01 | **понедельник** | ✅ да |

Спайк применил компенсацию бага 1900-високосного **поверх** якоря `1899-12-30`, который эту
компенсацию уже содержит — то есть вычел лишний день.

**3. Сверка по всем 11 листам (стандартная формула vs подпись в строке 2):**

```
лист            D1 серийник  стандарт Excel            D2 подпись
1-7 июня        46174        2026-06-01 (понедельник)  Понедельник
8-14 июня       46181        2026-06-08 (понедельник)  Понедельник
15-21 июня      46188        2026-06-15 (понедельник)  Понедельник
22-28 июня      46195        2026-06-22 (понедельник)  Понедельник
29-5 июля       46202        2026-06-29 (понедельник)  Понедельник
6-12 июля       46209        2026-07-06 (понедельник)  Понедельник
13-19 июля      46216        2026-07-13 (понедельник)  Понедельник
20-26 июля      46223        2026-07-20 (понедельник)  Понедельник
27-02 августа   46230        2026-07-27 (понедельник)  Понедельник
3-9 августа     46239        2026-08-05 (среда)        Среда
10-16 августа   46246        2026-08-12 (среда)        Среда
```

Совпадение 11 из 11, включая два листа с «нестандартной» подписью «Среда» — что само по себе
подсказка к Б-3 (у этих листов другая раскладка, и колонка D там не первый день недели).

## Как закрыт

Тикет 01, ветка `release-1.4/feature/01-grid-format-parser`, коммит `df3d472`.

- `XlsxScheduleGridParser.excelSerialToDate` использует стандартное декодирование
  `LocalDate.of(1899, 12, 30).plusDays(serial)` без второй компенсации;
- **правило «неделя начинается с дня X» из парсера убрано вовсе**: дата колонки = серийник,
  написанный над ней в строке 1. Поэтому вопрос «Пн или Вс первый» больше не может дать
  системную ошибку — файл сам решает;
- регресс-тест `excel_serial_conversion_matches_the_weekday_written_in_the_file` пиннит
  именно связку «46174 → 2026-06-01 → MONDAY», то есть сверку с подписью внутри файла;
- после исправления Б-1..Б-3 первый день **каждого** из 11 листов = понедельник, а даты
  сходятся с именами листов («3-9 августа» → 2026-08-03, «10-16 августа» → 2026-08-10).

## Что осталось владельцу

Утверждения в `spike/RESULT.md` (находки 1 и 3) и производные строки в `spec.md` остаются
как есть — они часть исторического артефакта разведки. Правки внесены в
`issues/01-grid-format-parser.md` (действующий контракт тикета). Статус самого спайка
меняет только владелец.
