## Problem Statement

WOLF умеет отвечать на вопрос «сколько времени я на это потратил» и «когда это закончится при такой ставке часов». Он не умеет отвечать на вопрос, ради которого всё затевалось: **«я потратил 120 часов — и что теперь у меня есть?»**

Владелец системы ведёт этот учёт вручную, вне WOLF. В его рабочей книге `Дорожная карта.ods` есть отдельный лист, названный «Бэклог необходимых достижений и артефактов», и в нём не задачи, а предъявляемые предметы:

- Сертификат ISTQB
- Проект на гитхаб с документацией
- Проект на гитхаб с развёрнутым Allure
- Видео со своей песней

Тот же смысл продублирован в колонке `Теги` реестра проектов строкой «фиксация результата» — ею помечены строки `10004 Сдать ISTQB`, `10005 Изучение теории Java`, `30004 Притянуло чернилами тень`. То есть пользователь **уже** делит проекты на «просто идёт работа» и «должен остаться артефакт», но система об этом различии не знает.

Три следствия отсутствия этой сущности:

1. **Проект закрывается по часам, а не по результату.** Статус `IN_PROGRESS → DONE` ставится вручную и ничем не обоснован. «60 часов на ISTQB» и «сданный экзамен ISTQB» — разные события, и первое не влечёт второго.
2. **Прогресс обучения невидим.** Профессия «QA-engineer FullStack Auto» — это четыре артефакта из списка выше. Сколько из них уже есть — система не показывает, потому что не хранит.
3. **Свидетельство теряется.** Номер сертификата, ссылка на репозиторий, ссылка на видео живут в заметках, письмах и памяти. Через год «докажи, что ты это сделал» упирается в поиск по почте.

## Solution

Вводится сущность **Артефакт** — предъявляемый результат, принадлежащий Проекту.

У Артефакта есть название, необязательная дата-цель, статус (`нет` / `есть`) и **Свидетельство** — то, чем его наличие доказывается: ссылка, текст или и то и другое («сертификат №CTFL-2026-1234», `https://github.com/…`).

Проект с Артефактами получает **вторую шкалу прогресса**: не «часы», а «предъявленные результаты — 2 из 4». Обе шкалы живут рядом на Дорожной карте и в карточке проекта. Проект без Артефактов остаётся полностью валидным — это рутинная работа, у которой нет и не должно быть предмета на выходе.

Артефакт **не потребляет часов**, не участвует в нагрузке, не имеет приоритета и не влияет ни на один существующий расчёт. Он ортогонален всей системе планирования — это её вторая ось, а не надстройка над первой.

## User Stories

1. Как пользователь, я хочу добавить проекту Артефакт «Сертификат ISTQB», чтобы зафиксировать, чем именно закончится этот проект.
2. Как пользователь, я хочу отметить Артефакт полученным и приложить номер сертификата, чтобы доказательство хранилось вместе с проектом, а не в почте.
3. Как пользователь, я хочу приложить к Артефакту ссылку на репозиторий или видео, чтобы одним кликом попасть на результат из карточки проекта.
4. Как пользователь, я хочу видеть на Дорожной карте «2 из 4» рядом с проектом обучения, чтобы понимать прогресс по результатам, а не только по часам.
5. Как пользователь с проектом без артефактов (рутинная работа), я хочу не видеть пустую шкалу и не получать предложений её заполнить, чтобы система не требовала предмета там, где его нет.
6. Как пользователь, я хочу задать Артефакту дату-цель, чтобы «Сдать ISTQB до декабря» было видно на Дорожной карте.
7. Как пользователь, я хочу увидеть все Артефакты всех проектов одним списком, чтобы получить свой «бэклог достижений» — тот самый лист из моей таблицы.
8. Как пользователь, я хочу отменить отметку о получении Артефакта, если поставил её по ошибке, чтобы действие было обратимым.
9. Как пользователь, закрывающий проект, у которого не все Артефакты получены, я хочу увидеть спокойную констатацию факта и закрыть проект, а не получить блокировку.
10. Как пользователь, я хочу, чтобы Артефакты попадали в экспорт и импорт данных, чтобы не потерять их при переносе на другой сервер.

## Implementation Decisions

### Модель

Новая таблица `artifact`. Следующий свободный номер миграции на момент написания — `V39__artifact.sql`; **тикет обязан сверить актуальный максимум** перед созданием файла:

```bash
ls api/src/main/resources/db/migration | sed 's/^V\([0-9]*\)__.*/\1/' | sort -n | tail -1
```

```sql
CREATE TABLE IF NOT EXISTS artifact (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
    project_id BIGINT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
    title VARCHAR(200) NOT NULL,
    description TEXT,
    target_date DATE,
    obtained_at DATE,
    evidence_text VARCHAR(500),
    evidence_url VARCHAR(1000),
    position INTEGER NOT NULL DEFAULT 0,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_artifact_project ON artifact (project_id, position);
CREATE INDEX IF NOT EXISTS idx_artifact_user ON artifact (user_id, obtained_at);
```

Решения по полям:

- **Статус — это `obtained_at`, а не булев флаг.** «Есть» = дата заполнена, «нет» = `NULL`. Дата получения нужна пользователю всё равно, а отдельный `boolean obtained` рядом с ней породил бы два источника правды и вопрос «что если флаг true, а даты нет».
- **`user_id` денормализован** при наличии `project_id`. Так сделано в `project_dependency` (`V19`), и по той же причине: изоляция арендатора проверяется одним предикатом, без join к проекту в каждом запросе.
- **Два поля свидетельства, не одно.** `evidence_text` — «сертификат №CTFL-2026-1234», `evidence_url` — ссылка. Одно поле заставило бы UI гадать, рисовать ли ссылку. Оба необязательны: Артефакт можно отметить полученным, ничего не приложив.
- **Файлы не храним.** Только ссылка и текст. Загрузка файлов — отдельное решение с вопросами о размере хранилища и бэкапе, см. Out of Scope.
- **`position`** — ручной порядок внутри проекта, как пользователь их перечислил. Не приоритет: у Артефакта нет приоритета по определению (см. ниже).

### Почему не `Goal` и не `GoalMetric`

В системе уже есть `Goal` (`V12__create_goals.sql`) со связкой `goal_project`, недельными бюджетами `goal_week_budget` и метриками `goal_metric`, у которых с `V30` есть `target_value`. Выразить артефакт как метрику `kind='сертификат', value=0, target_value=1` технически возможно, и это решение **отклонено**:

- `Goal` несёт `priority INTEGER NOT NULL` с ограничением `uq_goal_user_priority` — уникальным на пользователя. Артефакты не упорядочиваются глобально: «сертификат ISTQB» и «видео со своей песней» не сравнимы по приоритету и не должны занимать номера в одной очереди.
- `Goal` распределяет **часы** (`goal_week_budget`). Артефакт часов не потребляет.
- `goal_metric.value` — `NUMERIC(19,4)`. Свидетельство «сертификат №CTFL-2026-1234» в числовое поле не ложится, а добавление к метрике текстовых полей превратило бы её в свалку.

Цель отвечает на вопрос «куда я вкладываю часы на этой неделе». Артефакт отвечает на вопрос «что у меня останется». Это ортогональные оси, и связывать их одной таблицей — ошибка моделирования, которую потом придётся распутывать.

Связь между ними допустима и естественна через Проект: Цель ссылается на Проект (`goal_project`), Артефакт принадлежит Проекту. Прямой связи `goal ↔ artifact` в 1.1 нет — см. Out of Scope.

### API: `/api/v1/projects/{projectId}/artifacts`

Артефакт не существует вне Проекта, поэтому вложенный ресурс, а не корневой:

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v1/projects/{projectId}/artifacts` | список артефактов проекта в порядке `position` |
| `POST` | `/api/v1/projects/{projectId}/artifacts` | создать |
| `PUT` | `/api/v1/projects/{projectId}/artifacts/{id}` | изменить название, описание, дату-цель, свидетельство |
| `POST` | `/api/v1/projects/{projectId}/artifacts/{id}/obtain` | отметить полученным |
| `DELETE` | `/api/v1/projects/{projectId}/artifacts/{id}/obtain` | снять отметку (обратимость, история 8) |
| `DELETE` | `/api/v1/projects/{projectId}/artifacts/{id}` | удалить |

Плюс один корневой эндпоинт для «бэклога достижений» (история 7):

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v1/artifacts?obtained=all\|yes\|no` | все Артефакты пользователя со ссылкой на проект |

`POST /obtain` принимает `{ obtainedAt?, evidenceText?, evidenceUrl? }` — все поля необязательны, `obtainedAt` по умолчанию сегодня. Одно действие «отметил и приложил доказательство» не должно требовать двух запросов.

**Слоистая архитектура обязательна.** Релиз 0.9 переводит `wolf-api` на `Controller → Service → Repository` с DTO-records в `dto/`. Новая фича пишется **сразу по целевому паттерну**: `ArtifactController` (только HTTP, валидация, authentication) → `ArtifactService` (`@Transactional`, бизнес-логика) → `ArtifactRepository`; Request/Response — Java records в `ru.wolf.api.artifact.dto` со статическими фабричными методами `from(...)`. Контроллер **не инжектит репозиторий**. Это единственная фича, которую 0.9 не должен будет мигрировать задним числом.

### Вторая шкала прогресса

`GET /api/v1/projects/{id}` дополняется блоком (отсутствует, если у проекта нет Артефактов):

```jsonc
"artifacts": { "total": 4, "obtained": 2, "nextTargetDate": "2026-12-01" }
```

Тот же блок добавляется в ответ `GET /api/v1/planning/load-charts` (релиз 0.8) на уровне проекта, чтобы Дорожная карта показывала обе шкалы из одного запроса и они не могли разойтись.

Формулировка в UI — **«результаты: 2 из 4»**, не проценты и не прогресс-бар. Процент выполнения — оценочная цифра, а WOLF показывает дельту (принцип из `docs/method/wolf-methodology.md`, раздел 0).

### Закрытие проекта с неполученными Артефактами

Перевод проекта в `DONE` при наличии Артефактов без `obtained_at` **разрешён**. Показывается текстом: «2 из 4 результатов не получены». Ни блокировки, ни модального подтверждения, ни красного цвета — ровно тот же тон, что «перебор на N часов» в релизе 0.8.

### UI

**`ProjectDetailView.vue`** — секция «Артефакты» после описания проекта: список строк «название · дата-цель · статус», действие «отметить полученным» с полями свидетельства, «добавить артефакт». Полученный Артефакт показывает дату и свидетельство: `evidence_url` — ссылкой (`target="_blank" rel="noopener noreferrer"`), `evidence_text` — моноширинным текстом.

**`PlanningView.vue` (`/roadmap`)** — в строке проекта рядом с датой финиша появляется «результаты: 2 из 4». Только для проектов, у которых есть Артефакты; у остальных место остаётся пустым, колонка не добавляется.

**Новый маршрут `/artifacts`** — «Бэклог достижений»: плоский список всех Артефактов с группировкой по проекту и фильтром «все / получены / не получены». Пункт меню — в группе **«Управление потоком»** рядом с «Цели» (`web/src/App.vue`, группа `flow`), поскольку это про смысл и результат, а не про распорядок дел.

Визуальный контракт — тихая система 0.3: токены `--wolf-ink`, `--wolf-muted`, `--wolf-rule`, `--wolf-subrule`; без иконок-галочек, без бейджей, без теней и скруглений; `font-variant-numeric: tabular-nums` на счётчиках и датах. Полученный Артефакт отличается от неполученного **насыщенностью текста**, а не цветом и не зачёркиванием (зачёркивание читается как отмена, а не как достижение).

### Синхронизация данных

`DataSyncContract` дополняется листом:

```
sheet("artifacts", "externalId", "projectExternalId", "title", "description",
      "targetDate", "obtainedAt", "evidenceText", "evidenceUrl", "position")
```

Правила существующего механизма соблюдаются без изменений: upsert по `externalId`, разрешение связи через `projectExternalId`, ничего не удаляется молча. Затрагиваются `DataSyncExportService`, `DataSyncImportService`, `DataSyncImportApplyService`, `SyncExternalIdService`.

`UserPurgeService` дополняется удалением Артефактов (каскад по `user_id` уже покрывает, но сервис ведёт явный список — расхождение поймает `ProfilePurgeIT`).

### Демо-профиль

`DemoFixtureGenerator` добавляет Артефакты хотя бы одному обучающему проекту демо-профиля: два получены, два нет — чтобы вторая шкала была видна сразу после первого запуска, а не только после ручного заполнения.

## Testing Decisions

- `ArtifactApiIT`: полный CRUD; создание артефакта в чужом проекте → 404 (изоляция арендатора, не 403 — существование чужого проекта не подтверждается).
- `ArtifactApiIT`: `POST /obtain` без тела ставит `obtainedAt = сегодня`; с телом — переданную дату и свидетельство; повторный вызов идемпотентен (перезаписывает, не дублирует).
- `ArtifactApiIT`: `DELETE /obtain` возвращает артефакт в состояние «нет» — `obtained_at` становится `NULL`, свидетельство **сохраняется** (пользователь снял отметку по ошибке, доказательство терять нельзя).
- `ArtifactApiIT`: `GET /api/v1/artifacts?obtained=no` не возвращает полученные; `?obtained=all` возвращает все; чужие артефакты не появляются ни при одном фильтре.
- `ArtifactApiIT`: валидация — пустой `title` → 400; `title` длиннее 200 → 400; `evidence_url` длиннее 1000 → 400.
- `ProjectApiIT` (дополнение): `GET /projects/{id}` у проекта без артефактов **не содержит** блок `artifacts`; с артефактами — содержит верные `total`/`obtained`.
- `ProjectApiIT` (дополнение): перевод проекта в `DONE` с неполученными артефактами возвращает 200, статус меняется — закрытие не блокируется.
- `ProjectApiIT` (дополнение): удаление проекта удаляет его артефакты (каскад).
- `LoadChartsApiIT` (дополнение): блок `artifacts` присутствует в ответе `/planning/load-charts` и совпадает с тем, что отдаёт `/projects/{id}` — две шкалы из одного источника.
- `DataSyncApiIT` (дополнение): экспорт → импорт в чистый профиль восстанавливает артефакты со связью с проектом и датами; повторный импорт того же файла ничего не дублирует (upsert по `externalId`).
- `ProfilePurgeIT` (дополнение): после purge артефактов пользователя не остаётся.
- Слоистая архитектура (гейт релиза 0.9): `grep -l "private final.*Repository" api/src/main/java/ru/wolf/api/artifact/*Controller.java` пуст; Request/Response — records в `artifact/dto/`.
- Тихий контракт 0.3: инспекция DOM секции артефактов — нет `red`/`--wolf-danger`, нет `role="alert"`, нет `text-decoration: line-through` на полученных, нет прогресс-бара.
- Ручная приёмка: создать артефакт → отметить полученным со ссылкой → перезагрузить `/roadmap` → «результаты: 1 из 1» видно у проекта; перейти по ссылке из карточки.
- Гейт визуальных тикетов (обязательный, `wolf-life-os`): сборка → пересоздание контейнеров → сверка хэшей `web/dist` с отдаваемыми → аутентификация через `#/`-маршрут → инспекция DOM.

## Out of Scope

- **Загрузка файлов как свидетельства** — только ссылка и текст. Файловое хранилище ставит вопросы объёма, бэкапа и переноса при self-hosting; решается отдельно, если понадобится.
- **Прямая связь `Цель ↔ Артефакт`** — связь идёт через Проект. Прямое ребро добавляется только при доказанной потребности, а не «на будущее».
- **Артефакты у Дела и у Рутины** — Артефакт принадлежит Проекту. Дело — переиспользуемый тип активности, у него нет уникального результата по определению.
- **Автоматическое закрытие проекта при получении всех Артефактов** — нарушает принцип «ни одного решения за пользователя».
- **Шаблоны артефактов** («стандартный набор для проекта обучения») — преждевременно, пока нет ни одного заполненного профиля.
- **Проценты, прогресс-бары, бейджи и любая геймификация** — прямо отменено визуальным контрактом 0.3 и разделом «Что сознательно не берём» методологии.
- **Напоминания о приближении `target_date`** — уведомления как канал в 1.1 не вводятся.
- **Публичная страница достижений / шеринг** — 0.1 не имеет совместного доступа, вне модели.

## Тикеты

Живут в `.scratch/release-1.1-artifacts/issues/`. Тикет 01 блокирует все остальные.

```
01 ──┬── 02  Карточка проекта
     ├── 03  Дорожная карта + вторая шкала
     ├── 04  Бэклог достижений (/artifacts)
     └── 05  Синхронизация, purge, демо
```

01. Бэкенд: миграция, модель, `ArtifactService`, вложенный API, блок `artifacts` в ответе проекта — блокирует 02–05
02. UI: секция «Артефакты» в `ProjectDetailView.vue`
03. UI: вторая шкала на Дорожной карте + блок в `/planning/load-charts`
04. UI: маршрут `/artifacts`, пункт меню в группе «Управление потоком»
05. Синхронизация данных, `UserPurgeService`, демо-профиль

## Further Notes

**Термин заводится в `CONTEXT.md` тикетом 01, до написания кода.** Черновик статьи глоссария:

> **Артефакт**:
> Предъявляемый результат Проекта: предмет, документ или публикация, наличие которых доказывает, что Проект состоялся. Принадлежит одному Проекту, не потребляет часов, не участвует в расчёте нагрузки и не имеет приоритета. Статус — «есть» (заполнена дата получения) или «нет».
> _Avoid_: Веха (это про дату, не про предмет), Цель (это про приоритет и часы), Задача, Достижение как награда, Milestone
>
> **Свидетельство**:
> То, чем доказывается наличие Артефакта: ссылка, текстовый идентификатор или оба. Необязательно — Артефакт можно отметить полученным, ничего не приложив.
> _Avoid_: Вложение, Файл (файлы в 1.1 не хранятся), Пруф

**«Веха» сознательно отвергнута.** Владелец выбрал «Артефакт» при обсуждении методологии: веха — это точка на оси времени, а речь идёт о предмете, который остаётся после. Слово «веха» не должно появиться ни в UI, ни в коде.

**Источник требований — не выдуманный пример.** Список в Problem Statement — реальный лист «Цели и вехи» из рабочей книги владельца (`Дорожная карта.ods`). При этом сами эти данные в код WOLF **не переносятся**: как и в релизе 0.8, единственный источник предзаполненных данных — демо-профили релиза 0.6.

**Это первая фича, написанная сразу по паттерну 0.9.** Порядок релизов позволяет не делать работу дважды: если эта фича будет написана по старой конвенции (репозиторий в контроллере, `@Data`-классы в теле контроллера), тикет 11 карты 0.9 («сквозной аудит») найдёт его как новый долг. Тикет 01 обязан свериться с `.scratch/wayfinder-release-0.9-layered-arch/issues/01-pattern-adr-reference-migration.md` и с ADR, который тот тикет создаёт.
