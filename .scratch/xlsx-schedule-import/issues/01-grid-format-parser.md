# 01: Парсер формата недельной сетки Excel

**What to build:** Детерминированный парсер, который читает реальный `Расписание.xlsx`
(недельная сетка) в промежуточную модель — список записей `(дата, время начала, текст
активности)` — готовую к материализации в Записи времени. Парсер знает конкретный формат
владельца и не полагается на прежние (неверные для этого файла) допущения `XlsxImportService`.

**Blocked by:** None (can start immediately)

**Status:** resolved (ветка `release-1.4/feature/01-grid-format-parser`, коммит `df3d472`)

**Заводит баги:** `bugs/01` (сдвиг дат на сутки), `bugs/02` (формулы вместо чисел),
`bugs/03` (раскладка листов не одна) — три дефекта **артефакта разведки**, найденные при
реализации этого тикета прогоном прод-парсера на реальном файле.

Формат (уточнён при реализации; ⚠️ отмечены пункты, где спайк ошибся — см. `bugs/01-03`):
- лист = неделя; имя листа («1-7 июня») даты НЕ содержит;
- **row 1** — даты-серийники Excel; **row 2** — заголовки дней;
- ⚠️ **колонки сетки НЕ фиксированы**: на 9 листах время в C, дни в D–J; на последних двух
  («3-9 августа», «10-16 августа») всё сдвинуто на две колонки влево — время в A, дни в B–H.
  Раскладку определять по строке дат каждого листа, а не задавать константами (`bugs/03`);
- ⚠️ **никакого сдвига дней нет**: колонка D = **понедельник**, что подтверждают подписи
  строки 2 самого файла на всех 11 листах. Утверждение спайка «D = воскресенье» — следствие
  ошибки декодирования серийника на сутки назад (`bugs/01`). Правило «неделя начинается с
  дня X» парсеру не нужно вовсе: дата колонки = серийник, написанный над ней;
- ⚠️ **даты (кроме первой) и ВСЕ ячейки времени записаны формулами** — проверка
  `getCellType() == NUMERIC` в POI даёт ноль ячеек; нужен разбор
  `getCachedFormulaResultType()` (`bugs/02`);
- время — дробь суток в колонке времени; слоты встречаются в диапазоне 00:00–23:45
  (утверждение «день начинается ~07:00» верно лишь для первых листов, правилом не является);
- активности — в колонках дней тех строк, где в колонке времени стоит дробь;
- внизу листа блок «Факт» (часы по категориям) — игнорировать; справа на сдвинутых листах
  есть боковой блок («Задачи на неделю») — он не восьмой день, отсекать.

- [x] Колонки дней и колонка времени определяются **по строке дат каждого листа**, а не константами; правило «первый день недели» не используется (`bugs/03`)
- [x] Числа читаются и из формульных ячеек (`getCachedFormulaResultType`) — иначе файл даёт ноль ячеек (`bugs/02`)
- [x] Активности берутся только из строк-слотов; блок «Факт», строки вне сетки и боковой блок справа не попадают

## Answer

Реализовано отдельным классом `XlsxScheduleGridParser` (feature `importxlsx`), а не правкой
инлайн-разбора в `XlsxImportService`: тикет требует промежуточную модель, готовую к
материализации, и её же будет переиспользовать preview-слой тикета 02. Запись в БД парсер не
делает вовсе.

Ключевое отличие от плана: **три допущения формата из спайка оказались неверными**, и все три
всплыли только на прогоне прод-парсера (POI) по реальному файлу — на сыром XML, который читал
спайк, они не видны. Каждое заведено баг-файлом с доказательством: `bugs/01` (даты на сутки
назад → ложный вывод «D = воскресенье»), `bugs/02` (формульные ячейки → ноль записей),
`bugs/03` (раскладка сетки различается между листами → мусорная активность «0» и потеря двух
недель). Отсюда же правки в описании формата выше.

Практический вывод для тикетов 02–06: числа и утверждения `spike/RESULT.md` — гипотезы, а не
факты; проверять прод-кодом на реальном файле.
