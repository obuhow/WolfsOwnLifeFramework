## Вопрос

Переработать существующий движок тура из «обзора меню» (6 шагов, шаг = клик по пункту NAV)
в **сценарный движок** на 15 шагов, где шаг может завершаться тремя разными событиями:
кликом по пункту NAV, кликом по кнопке внутри страницы или **успешным сохранением сущности**
(ответ API). Добавить 🐺 и счётчик «шаг N из 15» под ADR-0007.

Это фундамент релиза: тикеты 02–06, 08, 09 наполняют движок конкретными шагами и без него
их некуда встраивать.

## Что есть сейчас (доказательство контекста)

`web/src/components/OnboardingTour.vue` (409 строк, релиз 0.6, тикет 03 `resolved`):

- `STEPS` — массив из **6** элементов, у каждого только `{ key, title, text }`
  (`:43-74`), где `key` — значение `data-tour-target` пункта NAV;
- шаг засчитывается **исключительно** кликом по узлу с совпадающим `data-tour-target`:
  `onCaptureClick` (`:257-266`) — `if (key !== step.value.key) return; advance(target)`.
  Клик слушается в фазе перехвата, потому что триггеры групп в `App.vue` гасят всплытие;
- геометрия выреза, четыре полосы затемнения, `ensureVisible()`, `measure()` в rAF-цикле
  (`:96-249`) — **переиспользуется как есть**, это отлаженная часть (в 0.6 через неё
  прошли три исправленных дефекта, см. «Найденные и исправленные дефекты» тикета 0.6-03);
- состояние: `onboardingTour.js:34` — `const active = ref(false)`, **в памяти вкладки**;
  `stepIndex` живёт локальным `ref` внутри компонента (`:84`) и перезагрузку не переживает;
- кнопка выхода уже есть: `exitLabel` = «Пропустить» / «Завершить» на последнем шаге
  (`:92,342`) — **третье сквозное требование заявки уже выполнено**, доделывать нечего;
- мобильное поведение через drawer (`viaMenu`, `MENU_HINT`, `:76-79,192-207`) —
  переиспользуется.

Ограничение, которое надо снять: `advance()` (`:268-287`) двигает шаг по таймеру
(`setTimeout`, 500/1100 мс) сразу после клика. Для 15-шагового сценария этого мало — шаги
типа «Действие: **успешное сохранение проекта**» (заявка, шаг 6) должны ждать ответа API, а
не таймера.

## Что сделать

### 1. Модель шага: три типа завершения

Расширить элемент `STEPS` до формы:

```js
{
  key: 'morning',                 // для nav-шагов: значение data-tour-target
  n: 3,                           // номер шага для счётчика (1..15)
  title: '...',
  text: '...',
  await: 'nav' | 'click' | 'event',
  target: '[data-tour-target="morning"]' | '[data-tour-action="project-create"]',
  event: 'wolf:project-saved',    // только для await: 'event'
  placement: 'anchored' | 'center' // 'center' — модальное окно по центру (шаги 2 и 15)
}
```

- `await: 'nav'` — текущее поведение: клик по узлу с `data-tour-target`;
- `await: 'click'` — клик по **произвольному** элементу страницы, адресуемому селектором
  (кнопки «Добавить проект», «Создать Дело», свободный слот сетки). Для устойчивости к
  вёрстке ввести **новый атрибут-якорь `data-tour-action`** по образцу `data-tour-target`
  (тур только читает атрибуты, DOM не меняет — правило 0.6-03 п.1 сохраняем). Атрибуты
  расставляют тикеты 02–08 на своих экранах;
- `await: 'event'` — шаг ждёт **успешного сохранения**: компонент экрана после `res.ok`
  диспатчит на `document` кастомное событие (`wolf:project-saved`, `wolf:delo-saved`,
  `wolf:time-entry-saved`, `wolf:routine-saved`). Движок слушает `document` и двигает шаг
  только по факту события. Это единственный честный способ отличить «нажал Сохранить» от
  «сохранилось» — при ошибке валидации тур не должен уезжать вперёд.

Порядок и содержимое `STEPS` целиком задаётся тикетами 02–09; здесь — только каркас и
единый источник массива (оставить в `OnboardingTour.vue` либо вынести в
`web/src/onboardingSteps.js` — на выбор реализующего, но в одном месте).

### 2. Счётчик «шаг N из 15» и 🐺 (под ADR-0007)

- В подсказке добавить строку счётчика: текст `шаг {{ step.n }} из {{ total }}`,
  `total = 15`. **Только текст**, графит `--wolf-muted`, без заполняемой полосы и без
  процентов (ADR-0007: исключение ограничено текстовой формой).
- 🐺 — префикс заголовка/сообщения подсказки. Никаких других иконок и эмодзи оверлей не
  вводит.
- Прочие правила тихого контракта внутри оверлея **не отменяются**: `border-radius: 0`,
  `box-shadow: none`, без сигнальных цветов, графитовая рамка, затемнение
  `rgba(26,26,26,.42)` — как сейчас (`:347-408`).

### 3. Модальный режим подсказки (`placement: 'center'`)

Шаги 2 (приветствие) и 16 (финал) по заявке — «всплывающее окно по центру экрана», а не
подсказка у элемента. Добавить режим: `hole = null` (затемнение целиком, одна полоса — уже
поддержано `shades`, `:215-228`), подсказка центрируется. Для шага 2 цель следующего
действия («вкладка Утренний обход») при этом **должна остаться кликабельной** — иначе
пользователь не сможет продолжить: держать вырез под целью, а окно ставить по центру.

### 4. Устойчивость к перезагрузке (`sessionStorage`)

`stepIndex` и признак активности тура сохранять в `sessionStorage`, восстанавливать при
монтировании. Обоснование: 15-шаговый сценарий с созданием сущностей длиннее прежних шести,
и перезагрузка посреди тура иначе отбрасывает гостя на шаг 1, притом что созданные им
проект/дело/записи остаются — рассинхрон текста тура с состоянием данных.

Решение 0.6-03 п.4 («состояние тура **не сохраняется в БД**») остаётся в силе — меняется
только носитель клиентского состояния (память вкладки → `sessionStorage`). При выходе из
тура (`endTour`) ключи очищать.

### 5. Совместимость с повторным запуском из шапки

`finish()` (`:301-311`) различает первый вход (`isFirstRunTour()` → Финальный выбор) и
повторный запуск из NAV (→ `completeOnboarding()` + `/calendar?view=week`). Логику
**сохранить**. Но: при повторном запуске тур ведёт пользователя **создавать** проект, дело
и рутину в его настоящем аккаунте. Поведение шагов-действий при повторном запуске
согласовать в рамках тикета 09 (финал) — здесь достаточно не сломать существующую развилку.

### 6. Единое имя тура в UI

В NAV пункт называется «**Приветственный тур**» (`App.vue:87`), в тикете 0.6-03 и в
`aria-label` оверлея — «Знакомство» (`:328`). Привести к одному имени: **«Приветственный
тур»** (заявка Павла использует его же). Правка `aria-label`, заголовков и текстов —
глоссарий не трогаем, это UI-строка (grill реш. F).

## Testing Decisions

- **Три типа завершения шага:** nav-шаг засчитывается кликом по `data-tour-target`;
  click-шаг — кликом по `data-tour-action`; event-шаг **не** двигается по клику «Сохранить»
  при ошибке валидации (проверить: отправить форму с пустым обязательным полем — тур стоит),
  и двигается после успешного сохранения.
- **Счётчик и 🐺 (ADR-0007):** в DOM оверлея присутствует строка «шаг N из 15» и 🐺;
  инкремент N совпадает с фактическим шагом; `total` = 15. **Отдельно проверить область
  исключения:** в DOM страницы **под** оверлеем по-прежнему `progressBars=0`, эмодзи нет,
  `svgIcons=0`; счётчик и 🐺 присутствуют **только** внутри узлов оверлея.
- **Тихий контракт внутри оверлея:** `border-radius: 0`, `box-shadow: none`, отсутствие
  зелёного/красного — как в приёмке 0.6-03.
- **Перезагрузка посреди тура:** пройти до шага 5, перезагрузить страницу (F5) — тур
  возобновляется на шаге 5, а не на шаге 1.
- **«Пропустить» на произвольных шагах** (например 3, 8, 12) — выход как сейчас: первый
  вход → `#/onboarding/final`, повторный запуск → `/calendar?view=week`.
- **Мобильный проход** (390×780): drawer-механика не сломана — тур подсвечивает кнопку
  меню, ждёт открытия drawer, засчитывает клик внутри.
- **Регресс на дефекты 0.6-03:** раскрытая группа в drawer не уводит цель за нижний край
  (`ensureVisible`); нет livelock прокрутки; раскрытое десктопное подменю не перекрывает
  цель следующего шага.
- Гейт: `npm run build` в `web/` зелёный → пересоздание контейнера → сверка хэшей с
  `web/dist` → аутентификация в браузере → инспекция DOM.
