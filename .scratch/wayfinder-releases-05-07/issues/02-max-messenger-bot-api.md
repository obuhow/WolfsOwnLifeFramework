# Max (VK) Bot API: применимость для канала импорта WOLF

## Question

Существует ли публичное bot API у мессенджера Max, какие у него технические и юридические ограничения, и насколько дорого реализовать канал импорта заметок в WOLF через него (третий канал после чат-панели и Telegram)?

### ВЕРДИКТ: реализуемо с оговорками

Публичное bot API у Max существует, документация открыта анонимно (`dev.max.ru/docs-api`, база `platform-api2.max.ru`) и технически покрывает все потребности WOLF:

- **Webhook** на HTTPS/443 с секретом в заголовке `X-Max-Bot-Api-Secret` — прямой аналог Telegram.
- **Deep link** `max.ru/<bot>?start=<payload>` (до 128 символов) + событие `bot_started` — механизм привязки Max-аккаунта к аккаунту WOLF, идентичный Telegram `?start=`.
- **Текст до 4000 символов** — заметка на 10–15 строк (~500–1500 симв.) проходит с большим запасом.
- **Inline-клавиатура** с `callback`-кнопками — подтверждение создания записи («Да/Нет»), тот же паттерн, что и в тикете 10 (архитектура бота).
- **Скачивание вложений** — прямой GET по `payload.url`, даже проще Telegram (не нужен двухшаговый `getFile`).
- Официальная **OpenAPI 3.0 схема** в Go-репозитории `max-messenger/max-bot-api-client-go` позволяет сгенерировать типобезопасный Java-клиент.

Код — ориентировочно **4,5–7 человеко-дней**, примерно в 1,3–1,8 раза дороже Telegram-канала.

### Оговорки, обязательные к закрытию до старта разработки

1. **Бизнес-статус.** Бота **нельзя создать физлицу**. Нужен верифицированный через Госуслуги профиль самозанятого, ИП или юрлица-резидента РФ. Это внешнее условие, не зависящее от кода, и главный блокирующий гейт.
2. **Модерация.** Токен выдаётся **только после** проверки заявки (до 48 рабочих часов); любое изменение карточки бота отправляет его на повторную модерацию. Исход для бота личного назначения («дневник для себя») не гарантирован — требование «описание должно соответствовать деятельности организации/бизнеса» может не устроить модерацию для персонального инструмента.
3. **Сертификат Минцифры.** `platform-api2.max.ru` отдаёт сертификат УЦ «Russian Trusted Sub CA», отсутствующий в стандартных truststore — подтверждено технически (`curl` падает с ошибкой проверки цепочки). Без импорта корневого сертификата в `cacerts` JVM исходящие вызовы из Spring Boot не заработают.
4. **Юридические обязательства.** Разработчик становится самостоятельным оператором ПДн: обязательна публичная политика обработки данных, пользовательское соглашение с явным принятием, готовность подтвердить правовое основание обработки по запросу VK за 3 календарных дня.
5. **Правовой риск п. 1.5 Требований.** Запрет на «Авторизационные, Транзакционные и Сервисные сообщения» через API. Для диалогового ответа бота («запись создана») риск оценён как низкий (это не рассылка, а прямой ответ на входящее сообщение пользователя), но для push-напоминаний по инициативе WOLF риск реальный и требует уточнения у VK.
6. **Голосовые сообщения не подтверждены.** Отдельного типа `voice` в схеме нет (0 вхождений при поиске по всей OpenAPI-спецификации). Есть поле `AudioAttachment.transcription` (потенциально готовая транскрипция от Max), но оно не описано в официальной документации — только в OpenAPI-схеме. Считать голосовой ввод через Max неподтверждённой функцией до проверки на живом боте.
7. **Эксплуатация webhook.** При 8 часах подряд неуспешных доставок бот автоматически отписывается от вебхука — нужен мониторинг подписки и автопереподписка.

### Сравнение с Telegram (уже работающим каналом WOLF)

| Фактор | Telegram | Max |
|---|---|---|
| Регистрация бота | @BotFather, ~2 минуты, любое физлицо | Верификация ИП/самозанятого через Госуслуги + модерация до 48ч |
| TLS к API | Обычный публичный CA | Требует импорт сертификата Минцифры в JDK truststore |
| Long polling в проде | Штатный режим | Явно запрещён документацией — только webhook |
| Java SDK | Зрелые библиотеки | Официального нет; официальная OpenAPI-схема есть |
| Юридические обязательства | Практически отсутствуют | Оператор ПДн + запрет на «сервисные сообщения» |
| Скачивание вложений | Двухшаговый `getFile` | Прямой `payload.url` — проще |

### Falsification (проверка недостоверных результатов поиска)

Показательно для доверия к исследованию: поисковый движок дважды предложил неверные факты, которые были опровергнуты прямой технической проверкой —
- Предложенный репозиторий `max-messenger/max-bot-api-client-java` — GitHub API вернул 404, репозитория не существует.
- `search.maven.org` по `ru.etsft.max` дал 0 результатов, но прямые пути `repo1.maven.org` отдают HTTP 200 — сторонняя библиотека `ru.etsft.max:max-bot-api-spring-boot:0.3.2` реально существует в Maven Central (индекс поиска просто отстаёт).

### Что не проверено (см. полное исследование, раздел «Что не удалось проверить»)

Точные лимиты long polling (только «ограничено», без цифр); формат заголовка `Authorization` (`Bearer` или голый токен — в документации замаскировано как `***`); приходят ли боту голосовые сообщения на практике и заполняется ли `transcription`; фактическая конфигурация TLS на `wolfs.smallmba.space`; трактовка VK формулировки «сервисные сообщения» применительно к диалоговому боту.

## Рекомендация по очерёдности

Оставить Max **третьим каналом**, как и запланировано в тикете 10 (после чат-панели и Telegram) — архитектура бота (сервис `ImportParserService`, разделение «разборщик / канал») уже спроектирована так, что добавление Max — это новый адаптер, а не переработка ядра. **Не начинать разработку кода до закрытия пп. 1–2** (верификация бизнес-профиля и успешная модерация с выданным токеном) — до этого момента написанный код физически нельзя ни протестировать, ни задеплоить.
