# Архитектура бота импорта: разборщик, каналы, связывание аккаунтов

Type: grilling
Status: resolved
Blocked by: 09

## Question

Как устроен бэкенд разбора, и как внешние мессенджеры получают доступ к аккаунту WOLF?

## Answer

### Переиспользование `NotesAssistant`

**Отдельный сервис `ImportParserService`.** У него свой промпт и контракт (структурированное извлечение сущностей по контракту тикета 09), `NotesAssistant` не трогается — он остаётся заточен под комментирование/подсказки на заметках, задачи разные.

### Структурированный вывод

**JSON Schema в промпте + structured output режим LLM API.** При невалидном ответе модели — **одна повторная попытка**, при повторной неудаче — деградация в «не разобрался» (по контракту тикета 09: сохранение как обычной Заметки в Личной базе знаний).

### Бюджет LLM на демо-стенде

**Собственный лимит запросов на гостя в день** (ориентир — 20 запросов/сутки). При превышении лимита — вежливый ответ без обращения к LLM («на сегодня лимит исчерпан, попробуйте завтра или сохраните текст как заметку»), не переключение на `FakeNotesAssistant` молча.

### Связывание Telegram-аккаунта

**Одноразовый код из Настроек**, который пользователь отправляет боту в Telegram. Бот получает код, ищет соответствующий pending-токен, привязывает `telegram_chat_id` к `userId`. Отвязка — кнопка в Настройках, удаляющая запись связки.

### Изоляция

**Явная передача `userId`, без синтетического SecurityContext.** Сервисы бота получают `userId` из таблицы связки `telegram_chat_id → userId` и передают его явным параметром в каждый вызов `ImportParserService` и сервисов создания сущностей. Нет неявного `Authentication`, кладущегося в `SecurityContextHolder` — путь бота архитектурно отделён от HTTP-пути, изоляция достигается тем, что `userId` в принципе не может быть перепутан (нет глобального «текущего пользователя» в контексте потока бота).

### Получение обновлений Telegram

**Webhook.** Домен `wolfs.smallmba.space` уже используется (HTTPS есть) — меньше нагрузка на сервер, быстрее доставка сравнительно с long polling.

### Граница разборщик/каналы

**Единый сервис, узкий контракт.** `ImportParserService.parse(userId, text) -> List<ParsedEntity>` — общий для всех каналов. Каналы (чат-панель, Telegram, в перспективе Max) отвечают **только за доставку текста внутрь и отрисовку карточки подтверждения наружу**, никакой логики разбора в каналах нет.

### Подтверждение в Telegram

**Не inline-кнопки с фиксированным набором действий, а поддержка редактирования полей через последовательные текстовые сообщения.** Telegram-канал воспроизводит ту же способность править поля до принятия, что и чат-панель (контракт тикета 09 — «карточка предпросмотра с редактируемыми полями» — соблюдается в обоих каналах одинаково, не урезается для Telegram). Технически: бот присылает карточку текстом + inline-кнопки Принять/Отклонить/Править конкретное поле; выбор «Править поле» переводит бота в режим ожидания следующего сообщения как новое значение этого поля.

### Голосовые сообщения

**Распространяются на импорт сразу**, в обоих каналах (чат-панель и Telegram) с самого начала — не поэтапно. `POST /api/v1/notes/audio` уже существует, используется как транспорт распознавания голоса в текст перед передачей в `ImportParserService.parse`.

### Хранение переписки

**Эфемерный поток.** История диалога с ботом не сохраняется как отдельная сущность. Хранится только результат — созданные Дела/Проекты/Рутины/Заметки. Отмена последнего разбора (вопрос из тикета 09, не решённый явно) реализуется через возможность удалить только что созданную сущность обычным способом (как любую другую), а не через откат истории чата.

### Тихий контракт

**Подтверждается явно.** Бот не инициирует сообщений сам — ни напоминаний, ни отчётов, ни «вы давно не записывали». Единственная инициатива бота — ответ на входящее сообщение пользователя (текст/голос) в рамках описанного потока разбор→карточка→подтверждение.

## Архитектурная схема

```
┌─────────────────┐     ┌──────────────────┐     ┌────────────────────┐
│  Чат-панель UI   │     │  Telegram Bot     │     │  Max Bot (0.7+)     │
│  (WOLF frontend) │     │  (webhook)        │     │  (по итогам research)│
└────────┬─────────┘     └────────┬──────────┘     └──────────┬──────────┘
         │ text/audio             │ text/audio/webhook          │
         │ userId (сессия)        │ userId (telegram_chat_id →) │
         ▼                        ▼                              ▼
┌──────────────────────────────────────────────────────────────────┐
│                    ImportParserService                            │
│  parse(userId, text) -> List<ParsedEntity>                        │
│  - JSON Schema + structured output, retry×1, деградация           │
│  - лимит LLM-запросов/день на гостя                                │
└────────────────────────┬───────────────────────────────────────────┘
                          ▼
              ┌───────────────────────┐
              │  Сущности WOLF          │
              │  (Дела/Проекты/Рутины/  │
              │   слоты, по контракту 09)│
              └───────────────────────┘
```

Готово к использованию в тикете 13 (публикация релиза 0.7).
