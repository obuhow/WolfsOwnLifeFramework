# Max (VK) Bot API — разведка для канала WOLF

**Дата исследования:** 23 августа 2026
**Контекст:** WOLF Life OS (Java 21 / Spring Boot 3 / Vue 3), VPS с публичным HTTPS-доменом `wolfs.smallmba.space`. Max планируется третьим каналом после веб-чата и Telegram. Основной сценарий — приём свободного многострочного текста заметки (дневник тренировки на 10–15 строк) и создание записи в системе.

## Обозначение типов источников

| Метка | Значение |
|---|---|
| **[ОФИЦ-ДОК]** | Официальная документация `dev.max.ru` — прочитана напрямую HTTP-запросом |

| **[НЕ ПРОВЕРЕНО]** | Проверить не удалось |

## 1. Существует ли публичное bot API

**Да, публичное bot API существует и документация открыта без авторизации.** [ОФИЦ-ДОК]

- URL документации API: **https://dev.max.ru/docs-api** — открывается анонимно, HTTP 200, полный SSR-контент (проверено curl). [ПРОВЕРЕНО-ТЕХ]
- Гайд по разработке ботов: **https://dev.max.ru/docs/chatbots/bots-coding/prepare** [ОФИЦ-ДОК]
- Базовый домен API: **`https://platform-api2.max.ru`** [ОФИЦ-ДОК]
  - Историческая цепочка доменов: `botapi.max.ru` → `platform-api.max.ru` → `platform-api2.max.ru`. Документация явно требует использовать `platform-api2.max.ru`. [ОФИЦ-ДОК]
  - `botapi.max.ru` ещё отвечает (HTTP 401 на `/me` без токена), то есть не выключен, но использовать его не следует. [ПРОВЕРЕНО-ТЕХ]

### Регистрация ботов — НЕ открыта всем. Это главное ограничение

Дословно из официальной документации: [ОФИЦ-ДОК]

> «Подключение к платформе MAX для партнёров и её сервисам — чат-ботам, мини-приложениям, каналам — доступно для **юрлиц, ИП и самозанятых, которые являются резидентами РФ**»
>
> «**Физические лица и нерезиденты пока не смогут пройти верификацию на платформе**»
>
> «Вы можете создать бота, **только если у вас есть верифицированный профиль организации, ИП или самозанятого** на платформе MAX для партнёров»

Порядок получения доступа: [ОФИЦ-ДОК]
1. Регистрация на платформе MAX для партнёров (веб-версия или мини-приложение «MAX для бизнеса») по номеру телефона + SMS.
2. Создание профиля юрлица / ИП / самозанятого.
3. **Верификация профиля через Госуслуги** (для ИП/юрлиц также T-Business ID или Alfa ID). Для самозанятых — только Госуслуги. Верификацию от организации может пройти только руководитель или представитель с правом первой/единственной подписи.
4. Создание бота в разделе «Чат-боты».
5. **Обязательная модерация — до 48 часов по рабочим дням.** Токен выдаётся только **после** успешной модерации.

Лимиты на количество ботов: [ОФИЦ-ДОК]

| Тип профиля | Ботов на профиль |
|---|---|
| Организация или ИП | 5 |
| Самозанятый | 2 |

Ник бота **генерируется автоматически и не выбирается**: `id<ИНН>_bot` для ИП/юрлиц, `se<orgid>_bot` для самозанятых. Изменить ник нельзя («Выбрать или изменить его пока нельзя»). [ОФИЦ-ДОК]

Статусы модерации: «на модерации» → «создан» либо «требует исправлений». В статусе «на модерации» настройки бота менять нельзя. **Любое изменение карточки бота возвращает его на повторную модерацию.** [ОФИЦ-ДОК]

> **Вывод по п.1:** API публичное и открыто документировано, но регистрация бота — **не свободная**. Требуется статус самозанятого / ИП / юрлица + верификация через Госуслуги + прохождение модерации. Это не «партнёрство по заявке» в смысле закрытой программы, а именно обязательный бизнес-статус. Для физлица без самозанятости — доступа нет.

## 2. Получение обновлений: long polling и webhook

Поддерживаются **оба** способа, но одновременно использовать нельзя — «Использовать одновременно оба типа нельзя — выберите один из них». При активной подписке на Webhook long polling не работает. [ОФИЦ-ДОК]

### Webhook — единственный рекомендованный для production [ОФИЦ-ДОК]

> «Для production-окружения — **только Webhook**»
> «Для разработки и тестирования — Webhook или Long Polling»

Подписка: `POST /subscriptions` с телом `{"url": "...", "update_types": [...], "secret": "..."}`.

**Требования к webhook-эндпоинту — жёсткие и явно перечислены:** [ОФИЦ-ДОК]

| Требование | Значение |
|---|---|
| Протокол | **Только HTTPS**, URL должен начинаться с `https://` |
| Порт | **Только 443.** Порт в URL не указывается. «Поддерживается только порт 443» |
| Сертификат | Выданный **доверенным центром сертификации** или **сертификат Минцифры**. **Самоподписанные не поддерживаются** |
| Домен | Доменное имя в URL должно совпадать с **CN или SAN** сертификата |
| Цепочка | Сервер обязан отдавать **полную цепочку сертификатов** |
| Таймаут ответа | HTTP 200 **в течение 30 секунд**, иначе — ошибка доставки |

С **25 мая** прекращена поддержка вебхуков по HTTP и самоподписанных сертификатов (в тексте документации указано «с 25 мая» без года; в разделе «Рекомендации по работе с API» — «с 25 мая 2026»). [ОФИЦ-ДОК]

**Политика повторов:** до 10 попыток с экспоненциальным ростом интервала (1-я через 60 с, 2-я через 150 с, 3-я через 375 с, множитель 2,5). **Если в течение 8 часов нет успешного ответа — бот автоматически отписывается от вебхука.** [ОФИЦ-ДОК]

**Защита:** необязательный, но настоятельно рекомендуемый параметр `secret` (регулярка `^[a-zA-Z0-9_-]{5,256}$`), приходит в заголовке **`X-Max-Bot-Api-Secret`** в каждом запросе. Документация прямо предписывает проверять его и отклонять несовпадающие запросы. [ОФИЦ-ДОК]

### Long Polling [ОФИЦ-ДОК]

`GET /updates` с параметрами `limit` (1–1000, по умолчанию 100), `timeout` (0–90 с, по умолчанию 30), `marker` (курсор), `types` (фильтр событий).

Документация трижды повторяет: «Получение обновлений с помощью Long Polling ограничено по скорости и сроку хранения событий — **этот способ не подходит для production-окружения**». Конкретные числовые лимиты по скорости и TTL событий в документации **не указаны**. [НЕ ПРОВЕРЕНО — точные цифры]

### Применимость к WOLF

`wolfs.smallmba.space` — публичный HTTPS-домен, что закрывает требование по HTTPS/443/домену. **Но:** требуется проверить, что сертификат от доверенного CA (Let's Encrypt подходит под «доверенный центр сертификации»), отдаётся полная цепочка, и эндпоинт слушает именно 443 без нестандартного порта. [НЕ ПРОВЕРЕНО — фактическая конфигурация TLS на wolfs.smallmba.space в рамках этого исследования не проверялась]

## 3. Аутентификация и связывание аккаунтов

### Токен бота [ОФИЦ-ДОК]

- Схема авторизации: `access_token`, тип `apiKey`.
- Передаётся **только заголовком** `Authorization`. Дословно: «Передача токена через query-параметры **больше не поддерживается** — используйте заголовок `Authorization: ***`».
- Где взять: «Чат-боты → Перейти → Расширенные настройки → Настроить» на платформе, либо в мини-приложении/боте «MAX для бизнеса» командой «Получить токен».
- Токен присваивается при создании бота и **доступен только после прохождения модерации**.
- «Токен **может быть отозван** за нарушение Правил платформы».

Примечание: в примерах документации значение заголовка показано как `Authorization: ***` без указания префикса (`Bearer` или голый токен). Точный формат по документации однозначно не определяется. [НЕ ПРОВЕРЕНО — конкретный формат значения заголовка]

### Deep link со start-параметром — ЕСТЬ, и это ровно то, что нужно для привязки аккаунта [ОФИЦ-ДОК]

Формат: `https://max.ru/<botName>?start=<payload>`

- `<payload>` — **до 128 символов**. «Если payload превышает 128 символов, он не будет передан боту».
- При переходе бот получает событие **`bot_started`** с полем `payload` в объекте `Update`.
- Для получения payload требуется Webhook или Long Polling; при Webhook нужно включить `bot_started` в `update_types`.

Пример объекта из документации:
```json
{
  "update_type": "bot_started",
  "timestamp": 1573226679188,
  "chat_id": 1234567890,
  "user": { "user_id": 1234567890, "name": "Иван", "username": "ivan_petrov" },
  "payload": "promo_summer2025"
}
```

Документация прямо описывает сценарий «Запуск бота через диплинк из внешнего приложения» — перенаправление пользователя из своего приложения/лендинга в бота с передачей контекста (идентификатор пользователя, номер заказа). Это в точности механика привязки аккаунта WOLF к аккаунту Max. [ОФИЦ-ДОК]

**Требование безопасности из документации:** «Не передавайте в payload конфиденциальные данные в открытом виде — используйте **одноразовые токены** или закодированные идентификаторы сессии». [ОФИЦ-ДОК]

**Юридическое ограничение на диплинки:** «Их использование не должно противоречить требованиям к содержанию и функциональности приложений. Например, **отправлять авторизационные сообщения через диплинки запрещено**». [ОФИЦ-ДОК] — Формулировка неоднозначна; связана с общим запретом на авторизационные сообщения (см. раздел 7). Для WOLF (привязка своего аккаунта одноразовым nonce, а не рассылка OTP-кодов) риск умеренный, но требует аккуратной трактовки. [НЕ ПРОВЕРЕНО — трактовка VK применительно к конкретному сценарию]

### Альтернатива — кнопка `request_contact` [ОФИЦ-ДОК]

Кнопка типа `request_contact` возвращает контакт и номер телефона, привязанный к аккаунту в Max. Сообщение содержит поле `hash`, которое можно верифицировать как `HMAC-SHA256(access_token, vcf_info)` — это подтверждает, что номер действительно принадлежит пользователю Max. Документация прямо называет это способом регистрации в чат-боте.

**Ограничение на использование данных:** «Данные пользователя (включая номер телефона), полученные с помощью кнопки `request_contact`, могут использоваться **только для взаимодействия с текущим чат-ботом**». [ОФИЦ-ДОК] — то есть привязывать номер к внешней учётке WOLF в широком смысле нужно очень осторожно; безопаснее использовать deep link + одноразовый токен.

## 4. Ограничения: rate limits, длина, форматирование, кнопки

### Rate limits [ОФИЦ-ДОК]

| Лимит | Значение |
|---|---|
| Общий на домен `platform-api2.max.ru` | **30 rps** |
| Отправка сообщений в один диалог/чат/канал | **не более 2 сообщений в секунду** |
| Код превышения | HTTP **429** |

Документация: «При превышении этого лимита сообщения следует ставить в очередь или делать задержку перед отправкой». [ОФИЦ-ДОК]

### Длина сообщения и многострочность

- **`text`: максимум 4000 символов.** Подтверждено дважды: в описании тела `POST /messages` [ОФИЦ-ДОК] и в OpenAPI-схеме (`NewMessageBody.text.maxLength: 4000`) [ОФИЦ-РЕПО].
- Для сравнения: Telegram — 4096 символов. Разница несущественна.
- **Многострочный текст:** отдельного запрета нет, поле `text` — обычная строка, форматирование поддерживает `blockquote`, заголовки и списки. Прямого утверждения «переносы строк поддерживаются» в документации нет, но косвенно подтверждается: в описании Markdown указано, что переводы строк особым образом обрабатываются **только внутри моноширинного блока** (`` `code` `` — «переводы строк внутри этого блока обрабатываются как пробелы»), что подразумевает нормальную обработку вне его. [ОФИЦ-ДОК, вывод по косвенным признакам — не прямое утверждение]

  Для сценария WOLF (заметка на 10–15 строк, ~500–1500 символов) лимит в 4000 символов с запасом достаточен. **Риск низкий.**

### Форматирование [ОФИЦ-ДОК]

Параметр `format` со значениями `markdown` или `html`.

Поддерживается: курсив, жирный, зачёркнутый, подчёркнутый (`++underline++` / `<u>`), моноширинный, ссылки, упоминания (`max://user/user_id`), выделенный (`^^text^^` / `<mark>`), заголовки (`#` / `<h1>`–`<h4>`, все уровни отображаются одинаково), цитаты (`>` / `<blockquote>`).

Отличия от Telegram: свой диалект Markdown с нестандартными конструкциями (`++underline++`, `^^выделенный^^`), заголовки и `<mark>` которых в Telegram нет. Прямой перенос форматтера из Telegram-канала невозможен — нужен отдельный рендерер.

### Интерактивные кнопки — ЕСТЬ, полноценный аналог inline keyboard [ОФИЦ-ДОК]

Вложение типа `inline_keyboard` в `attachments`, массив `payload.buttons` (массив массивов = ряды).

**Размерность:** до **210 кнопок**, сгруппированных в **30 рядов** по **до 7 кнопок** в ряду (до **3**, если это кнопки типа `link`, `open_app`, `request_geo_location`, `request_contact`).

**Типы кнопок:**

| Тип | Назначение |
|---|---|
| `callback` | Приходит событие `message_callback`. Документация прямо называет применение: «**подтвердить действие пользователя**» |
| `link` | Открывает ссылку (до 2048 символов) |
| `request_contact` | Запрос контакта и номера телефона |
| `request_geo_location` | Запрос геолокации |
| `open_app` | Открывает мини-приложение |
| `message` | Отправляет боту заранее заданный текст |
| `clipboard` | Копирует `payload` в буфер обмена |

Для ответа на callback есть метод `POST /answers` («Отправка ответа на callback»). [ОФИЦ-ДОК]

**Важное ограничение:** «Если переслать сообщение с кнопками из чат-бота в любой другой чат, кнопки не будут пересланы». [ОФИЦ-ДОК]

> Сценарий WOLF «подтверди создание записи кнопкой Да/Нет» — **полностью реализуем** через `callback`-кнопки + событие `message_callback`.

### События (`Update`) [ОФИЦ-ДОК]

`bot_added`, `bot_started`, `bot_stopped`, `bot_removed`, `chat_title_changed`, `dialog_cleared`, `dialog_muted`, `dialog_unmuted`, `dialog_removed`, `message_callback`, `message_created`, `message_edited`, `message_removed`, `user_added`, `user_removed`.

Для WOLF достаточно `message_created`, `bot_started`, `message_callback`.

## 5. Вложения: файлы и голосовые сообщения

### Отправка файлов ботом [ОФИЦ-ДОК]

Трёхшаговый процесс:
1. `POST /uploads?type={type}` → возвращает `url` для загрузки.
2. Загрузка файла на этот `url` (resumable либо multipart/form-data).
3. `POST /messages` с `attachments[].payload.token`.

Домен загрузки зависит от типа: `file` → `fu.oneme.ru`, `image` → `iu.oneme.ru`, `video` → `omub.okcdn.ru`, `audio` → `omu.okcdn.ru`. [ОФИЦ-ДОК]

Лимиты: image до 50 МБ и ≤7680×7680 px (оба критерия), video до 250 МБ, audio до 256 МБ и ≤60 мин, file до 4 ГБ. [ОФИЦ-ДОК]

Комбинирование: до 12 вложений (видео+изображения) + 1 клавиатура. **Файл (`file`) можно комбинировать только с клавиатурой** — вместе с изображением или видео не поддерживается, и только один файл на сообщение. [ОФИЦ-ДОК]

Документация предупреждает: сервер обрабатывает файл после загрузки, и отправка сообщения сразу после загрузки может вернуть ошибку — нужна задержка/ретрай. [ОФИЦ-ДОК]

### Скачивание входящих вложений [ОФИЦ-РЕПО]

В OpenAPI-схеме базовый объект `AttachmentPayload` содержит обязательное поле:
```yaml
AttachmentPayload:
  properties:
    url:
      description: |-
        Media attachment URL.
        For video attachments use getVideoAttachmentDetails method to obtain direct links.
  required:
    - url
```
`FileAttachmentPayload` и `MediaAttachmentPayload` наследуют `url` и добавляют `token`. `FileAttachment` дополнительно несёт `filename` и `size` (bytes).

> **Скачивание входящих файлов = прямой GET по полю `payload.url` из входящего вложения.** Для видео — через `getVideoAttachmentDetails`. Отдельного метода `getFile` (как в Telegram) нет — ссылка приходит сразу. [ОФИЦ-РЕПО]

### Голосовые сообщения — отдельного типа НЕТ

Проверено поиском по всей OpenAPI-схеме (114 583 байта): **вхождений `voice` — ноль**. [ПРОВЕРЕНО-ТЕХ]

Типы вложений в документации и схеме: `image`, `video`, `audio`, `file`, `sticker`, `contact`, `inline_keyboard`, `share`, `location`. Отдельного `voice` / `voice_message`, как в Telegram, **нет**. [ОФИЦ-ДОК + ОФИЦ-РЕПО]

**Но:** в схеме объект `AudioAttachment` содержит поле, крайне полезное для WOLF:
```yaml
AudioAttachment:
  properties:
    payload: MediaAttachmentPayload   # содержит url + token
    transcription:
      description: Audio transcription
      type: string
      nullable: true
```
[ОФИЦ-РЕПО]

То есть входящее аудио может приходить с **готовой транскрипцией на стороне Max**. Это потенциально снимает необходимость собственного STT.

**Однако не проверено:**
- Приходит ли голосовое сообщение, записанное пользователем в интерфейсе Max, как `AudioAttachment` (и заполняется ли `transcription`), или оно вообще не доставляется боту. [НЕ ПРОВЕРЕНО — требует живого бота]
- Условия и языки заполнения `transcription`, лимиты по длительности. В документации `dev.max.ru` поле `transcription` **не описано вовсе** — оно есть только в OpenAPI-схеме в Go-репозитории. [НЕ ПРОВЕРЕНО]

## 8. Отдельно: TLS-сертификат Минцифры — техническое препятствие для JVM

Документация в шапке **каждой** страницы API повторяет: [ОФИЦ-ДОК]

> «Для корректной работы ваших чат-ботов и мини-приложений направляйте запросы на домен `platform-api2.max.ru`... Также убедитесь, что **добавили сертификат Минцифры в список доверенных**».

Проверено технически (23.08.2026): [ПРОВЕРЕНО-ТЕХ]
```
$ openssl s_client -connect platform-api2.max.ru:443 -servername platform-api2.max.ru
issuer  = C=RU, O=The Ministry of Digital Development and Communications,
          CN = Russian Trusted Sub CA
subject = CN = *.max.ru, O = MAX LLC, C = RU, ...
notBefore = Jun  6 12:35:09 2026 GMT
notAfter  = Jun  6 12:35:09 2027 GMT

$ curl https://platform-api2.max.ru/me
curl: (60) SSL certificate problem: unable to get local issuer certificate
```

**Сервер API отдаёт сертификат, выпущенный УЦ Минцифры («Russian Trusted Sub CA»), который отсутствует в стандартных доверенных хранилищах** — ни в системном CA-бандле тестовой машины, ни, соответственно, в `cacerts` JDK.

**Последствие для WOLF:** исходящие вызовы `platform-api2.max.ru` из Spring Boot **упадут с `PKIX path building failed`**, пока корневой сертификат «Russian Trusted Root CA» не будет импортирован в truststore JVM (`keytool -importcert` в `$JAVA_HOME/lib/security/cacerts` или отдельный truststore через `-Djavax.net.ssl.trustStore`). Сертификат публикуется на Госуслугах (https://www.gosuslugi.ru/crt, HTTP 200 — проверено).

Это **решаемая, но обязательная** задача деплоя, которой нет в Telegram-интеграции. Дополнительный эксплуатационный долг: сертификат сервера истекает 06.06.2027, корневой сертификат нужно поддерживать в актуальном состоянии в образе/на VPS.

## 9. Сравнение трудозатрат с Telegram Bot API

### Что похоже (перенос архитектуры почти 1:1)
- HTTPS + JSON, плоский набор методов, токен в заголовке.
- Long polling и webhook, выбор одного из двух.
- Webhook-секрет в заголовке — прямой аналог Telegram `X-Telegram-Bot-Api-Secret-Token` (у Max — `X-Max-Bot-Api-Secret`).
- Inline-клавиатура с callback-кнопками и событием нажатия.
- Deep link `?start=<payload>` — механика идентична Telegram (`t.me/bot?start=`), даже лимит близок (Max 128 символов; Telegram 64).
- Лимит текста: 4000 против 4096 у Telegram.
- Markdown/HTML-форматирование.

### Что сложнее в Max

| Фактор | Telegram | Max | Влияние |
|---|---|---|---|
| Регистрация бота | @BotFather, ~2 минуты, любой физлицо | Верификация ИП/самозанятого через Госуслуги + модерация до 48 ч | **Блокирующее** |
| Ник бота | Выбирается свободно | Генерируется как `id<ИНН>_bot`, изменить нельзя | Косметика/приватность (ИНН публичен в ссылке) |
| TLS к API | Обычный публичный CA | Сертификат Минцифры, нужен импорт в JDK truststore | Средняя, разовая настройка + поддержка |
| Webhook-порт | 443, 80, 88, 8443 | **Только 443** | Малое (у WOLF и так 443) |
| Long polling в проде | Штатный режим | Явно запрещён документацией | Средняя — нужен webhook сразу |
| Автоотписка вебхука | Нет | **Через 8 ч неуспешных доставок бот отписывается** | Средняя — нужен мониторинг + переподписка |
| Java SDK | Зрелые (`telegrambots` и др.) | Официального нет; есть OpenAPI-схема и сторонняя 0.3.x | Средняя |
| Голосовые сообщения | Отдельный тип `voice` + `getFile` | Типа `voice` нет; есть `audio` с полем `transcription` (не задокументировано) | **Не проверено** |
| Юридические обязательства | Практически отсутствуют | Оператор ПДн, публичная политика, ответ VK за 3 дня, п. 1.5 о сервисных сообщениях | Средняя–высокая |
| Изменение карточки бота | Мгновенно | Повторная модерация | Малая |

### Что проще в Max
- Скачивание вложений: `payload.url` приходит сразу во входящем сообщении — не нужен двухшаговый `getFile` + сборка URL с токеном, как в Telegram.
- Входящее аудио потенциально приходит с готовой транскрипцией (`transcription`) — в Telegram нужен свой STT. **Не проверено.**
- Официальная OpenAPI-схема доступна публично — у Telegram Bot API официальной OpenAPI-спеки нет.

### Оценка трудозатрат (только код, без юр. и организационной части)

При наличии готового Telegram-канала в WOLF архитектура переиспользуется: тот же порт входящих сообщений, тот же парсер заметки, та же доменная логика. Отличается только адаптер.

| Работа | Оценка |
|---|---|
| HTTP-клиент + DTO (кодогенерация из OpenAPI либо ручные записи для ~10 методов) | 1–2 дня |
| Webhook-контроллер, проверка `X-Max-Bot-Api-Secret`, идемпотентность | 0,5–1 день |
| Управление подпиской `POST /subscriptions` + мониторинг автоотписки через 8 ч | 0,5–1 день |
| Привязка аккаунта через deep link `?start=<одноразовый токен>` + `bot_started` | 0,5–1 день |
| Callback-кнопки подтверждения + `POST /answers` | 0,5 дня |
| Рендерер форматирования под диалект Max (отличается от Telegram) | 0,5 дня |
| Импорт корневого сертификата Минцифры в truststore JVM + деплой | 0,5 дня |
| Rate limiting (30 rps глобально, 2 msg/s на чат) | 0,5 дня |
| **Итого код** | **~4,5–7 человеко-дней** |

Организационная часть **не параллелится и не ускоряется разработкой**: оформление самозанятости (если нет), верификация через Госуслуги, публикация политики конфиденциальности и пользовательского соглашения, прохождение модерации до 48 ч, возможные итерации при отказе. Реалистично — **от 1 до 3+ недель календарно**, с неопределённым исходом модерации.

> **Вывод:** по объёму кода Max примерно в **1,3–1,8 раза дороже** Telegram-канала. Но общая стоимость выхода определяется не кодом, а обязательным бизнес-статусом, модерацией и юридическими обязательствами оператора ПДн.

## ВЕРДИКТ

# Реализуем с оговорками

Публичное bot API у Max существует, полностью документировано и технически покрывает **все** потребности WOLF: webhook на HTTPS/443 с секретом в заголовке, deep link `?start=<payload>` до 128 символов с событием `bot_started` для привязки аккаунта, текст до 4000 символов (заметка на 10–15 строк проходит с запасом), inline-клавиатура с `callback`-кнопками для подтверждения действий, скачивание вложений прямым GET по `payload.url`. Официальная OpenAPI 3.0 схема в Go-репозитории позволяет сгенерировать Java-клиент; кода — ориентировочно 4,5–7 человеко-дней, примерно в 1,3–1,8 раза дороже Telegram-канала.

**Оговорки, каждая из которых обязательна к закрытию до старта:**
1. **Бизнес-статус.** Бота нельзя создать физлицу — нужен верифицированный через Госуслуги профиль самозанятого, ИП или юрлица (резидент РФ). Это внешнее по отношению к разработке условие и главный гейт.
2. **Модерация.** Токен выдаётся только после проверки до 48 рабочих часов; любое изменение карточки бота отправляет его на повторную модерацию. Исход для бота личного назначения не гарантирован.
3. **Сертификат Минцифры.** `platform-api2.max.ru` отдаёт сертификат «Russian Trusted Sub CA», отсутствующий в стандартных truststore — проверено, `curl` падает с ошибкой проверки. Без импорта корневого сертификата в `cacerts` JVM исходящие вызовы не заработают.
4. **Юридические обязательства.** Разработчик становится самостоятельным оператором ПДн: публичная политика обработки данных, пользовательское соглашение с явным принятием, готовность подтвердить правовое основание обработки по запросу VK за 3 календарных дня.
5. **Правовой риск п. 1.5** Требований: запрет на «Авторизационные, Транзакционные и Сервисные сообщения» через API. Для диалогового ответа бота риск оценивается как низкий, но для push-напоминаний по инициативе WOLF — реальный и требует уточнения у VK.
6. **Голосовые сообщения не подтверждены.** Типа `voice` в API нет; поле `transcription` есть только в OpenAPI-схеме и не описано в документации. Если голосовой ввод критичен для канала — считать функцию неподтверждённой до проверки на живом боте.
7. **Эксплуатация webhook.** При 8 часах неуспешных доставок бот автоматически отписывается — нужен мониторинг подписки и автопереподписка.

**Рекомендация по очерёдности:** оставить Max третьим каналом, как и запланировано. Разработку не начинать до закрытия п.1 (верификация профиля) и п.2 (успешная модерация с выданным токеном) — до этого момента любой написанный код нельзя ни протестировать, ни задеплоить, поскольку токен физически недоступен.
