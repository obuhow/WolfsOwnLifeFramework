## Problem Statement

Кнопка «＋» сейчас — **одноразовый парсер одной фразы** (`ImportChatPanel.vue` →
`/import/parse` → предпросмотр → `/import/confirm`): написал текст, получил кандидатов,
подтвердил. Это не диалог: нет истории, нет памяти, агент ничего не знает о пользователе —
он видит только присланную фразу.

Продуктовая цель владельца (см. `grill.md`): сбоку по кнопке «＋» — **полноценный чат с
управляющим агентом**, у которого в контексте **расписание, цели и базовая информация по
проектам** пользователя. Агент сопровождает планирование: отвечает, объясняет, предлагает
действия и — с подтверждением — выполняет их (создаёт/меняет/удаляет Записи времени, Дела и
т.п.). Тот же агент обслуживает и импорт неструктурированного текста — отдельного режима нет
(Р-C).

Две цели проекта разведены прожаркой и **не** конфликтуют: агент читает контекст текущего
пользователя, кем бы тот ни был — тобой (полгода реального факта, Р-I) или демо-гостем
(синтетический демо-профиль, Р-K). Wow демо обеспечивается не полнотой агента, а структурой
и сведением целей (Р-J/L); режиссура демо — отдельное исследование, вне этого направления (О-1).

## Solution

Превратить канал «＋» из парсера в **диалоговый чат с одним встроенным агентом-планировщиком**:

- **Один агент, одно окно** (Р-A/C). Системный промпт задаёт разработчик (Р-B); пользователь
  промпты не пишет. Импорт неструктурированного текста — тот же агент, отличаются лишь слова.
- **Контекст динамический** (Р-F): базовый узкий срез (активные проекты, цели, рутины) кладётся
  всегда; глубже (конкретный проект, история) агент дотягивает по ходу. Расписание передаётся
  **не сырыми Записями времени, а посчитанным кодом описанием динамики** за период (~полгода):
  часы по проектам/областям/рутинам, план vs факт, тренды — LLM интерпретирует поверх точных
  чисел, не выдумывает их (Р-G/H, Т-2). Источники агрегатов уже есть: `FactAggregateService`,
  `MorningDigestService`, `GoalService`, `RoutineService`, `ProjectService`.
- **Действия только через подтверждение** (Р-D/E): агент возвращает не только текст, но и
  **машинно-читаемое предлагаемое действие** (создать/изменить/удалить, с полями) — UI
  показывает превью и применяет по «Подтвердить» (Т-1). Перекраивать/удалять существующее
  можно, но всегда с подтверждением — соответствует запрету WOLF на молчаливое удаление/
  перезапись и «в одной ячейке не больше одной Записи». Применение переиспользует
  `ImportConfirmService` / `RecurrenceService` / доменные сервисы как инструменты.
- **Переписка хранится** между сессиями (Р-O): новые сущности `ChatSession`/`ChatMessage` +
  миграция Flyway (следующая — **V43**, последняя в репозитории V42). Прошлые сообщения — тоже
  часть контекста.
- **Модель из конфига** (Р-N): `wolf.llm.model`, без выбора в UI. Внешний LLM допустим с
  **прозрачностью контекста** (Р-M): пользователю видно, какой срез ушёл в модель.
- **Демо**: чат доступен демо-аккаунту на демо-данных с **лимитом запросов** (Р-K, паттерн
  `ImportBotDailyUsage`).

Архитектурно — точечный порт-адаптер по образцу `note/assistant` (интерфейс `AgentChatPort` +
`HttpAgentChatAdapter` `@Profile("!test")` / `FakeAgentChatAdapter` `@Profile("test")`), тонкий
`*Service` с `@Transactional`, контроллер только HTTP, DTO — records в `dto/` (архитектура
release 0.9, см. `AGENTS.md`).

## Судьба бага Б-1 (релиз 1.3, тихий no-op парсера)

Б-1 (`.scratch/release-1.3-tech-debt/bugs/01-import-chat-recurrence-silent-drop.md`) — дефект
текущего парсера: повторяющееся дело без времени молча не попадает в расписание. Решение
владельца требуется (в spec фиксируем развилку, выбор за владельцем):

- **вариант 1 — починить в релизе 1.3 параллельно**: парсер живёт до готовности чата; тихий
  no-op недопустим независимо от будущего чата (рекомендуется — не оставлять живой дефект);
- **вариант 2 — поглотить чатом**: логика подтверждения этого направления (тикет 04) заменяет
  парсер; Б-1 закрывается как «устарело» при мердже чата. Риск: пока чат не готов, дефект живёт.

Рекомендация: **вариант 1** (дешёвый фикс, не держит живой тихий провал), а тикет 04 всё равно
переиспользует `ImportConfirmService` — фикс не пропадёт.

## Приватность и стоимость (следствия решений)

- Контекст (реальные проекты/цели/динамика) уходит во внешний LLM — принято с прозрачностью
  (Р-M). Self-hosted для реального клиента возможен «бесплатно» через другой `wolf.llm.url` —
  отдельным тикетом не заводится.
- Демо-аккаунты ходят в LLM → лимит запросов обязателен (тикет 07), иначе публичное демо =
  неконтролируемый счёт.

## Версия

Направление функциональное (новая возможность) — по завершении MVP поднять минорную версию
синхронно в `web/package.json` и `api/build.gradle` (как в релизах 1.0/1.1/1.2). Номер —
решением владельца при планировании релиза, в который войдёт чат. Отдельным тикетом не
заводится: делается в финальном мердже.

## Out of Scope (MVP)

- Пользовательский конструктор агентов / собственные системные промпты (Р-B).
- Несколько агентов как отдельные сущности в UI — импорт живёт в том же одном окне (Р-C).
- Выбор LLM-модели в UI (О-2; исходная «модель на выбор» сознательно сужена до конфига, Р-N).
- Голосовой ввод в чат (`transcribe` в `AssistantPort` есть, но подключается отдельно).
- Полностью автономный агент без подтверждения (Р-D — отвергнут).
- Режиссура демо-wow и демо-сценарий (О-1 — отдельное исследование).
- Self-hosted-развёртывание LLM для клиента (конфиг-уровень, не код).
