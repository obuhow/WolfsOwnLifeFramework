## Исходная заявка владельца

Две цели проекта WOLF:
1. Демо-версии с **wow-эффектом** для владельцев бизнеса (цель — развернуть им такую же
   систему или разработать ERM под их бизнес).
2. Управляющий LLM-агент сопровождает планирование: сбоку по кнопке «＋» — полноценный чат
   с агентом (модель на выбор); у агента в контексте расписание, цели и базовая информация
   по проектам.

Уточнение по ходу: агент по умолчанию имеет в контексте **структурированные данные о
проектах пользователя**; возможны другие чаты с другим системным промптом (напр. импорт
неструктурированной информации в БД).

## Решения владельца

| # | Вопрос | Решение | Обоснование / следствие |
|---|--------|---------|--------------------------|
| Р-A | Один агент или несколько ролей? | **Агент = профиль** (системный промпт + срез данных в контексте + права). По умолчанию — «Планировщик» со структурированным контекстом проектов. | Роль зависит от того, чей контекст (твой / демо-профиля). Один механизм, не два продукта. |
| Р-B | Кто задаёт системные промпты? | **Разработчик** (встроенные профили в коде/конфиге). Пользователь их не пишет. | Конструктор агентов вне объёма. Безопаснее для демо: владелец бизнеса не сломает промпт. |
| Р-C | Сколько окон/агентов у пользователя? | **Одно окно, один агент.** Импорт неструктурированного текста — тот же агент, отличаются лишь слова пользователя. | Отдельной кнопки/режима «Импорт» нет. Агент по формулировке понимает: совет vs создать сущность vs разобрать свалку мыслей. |
| Р-D | Нужно ли подтверждение при записи в БД? | **Да — вариант (а): агент предлагает, применяет только после явного «Подтвердить».** | Соответствует духу WOLF «под контролем пользователя», запрету на «система додумывает». |
| Р-E | Может ли агент трогать существующее (удалять/перекраивать)? | **Да, но только с подтверждением.** Не ограничен «только добавлять». | Соответствует запрету WOLF на молчаливую перезапись/удаление; «в одной ячейке — не больше одной Записи». |
| Р-F | Объём контекста? | **Динамический (вариант в):** базовый узкий срез всегда, глубже агент дотягивает по ходу разговора. | Снимает «весь граф не влезет». |
| Р-G | Как передаётся расписание? | **Не сырыми Записями времени, а сформированным ОПИСАНИЕМ ДИНАМИКИ** (~последние полгода). | Дамп тысяч 15-мин ячеек за полгода бесполезен; нужна аналитическая сводка (часы по проектам/областям/рутинам, план vs факт, тренды). |
| Р-H | Кто формирует описание динамики? | **Код считает агрегаты детерминированно; LLM интерпретирует поверх точных чисел.** | Никаких выдуманных процентов. Для доверия (особенно бизнес-аудитории) критично. У WOLF уже есть `FactAggregateService`, план нагрузки, morning-digest. |
| Р-I | Есть ли реально полгода факта? | **У владельца — да**, данные есть. | Агент тестируется на живой истории, не на пустоте. |
| Р-J | Весь ли функционал агента идёт в демо? | **Нет.** Wow демо ≠ полный функционал агента; wow бывает и после демо. | Не пихать весь агент-функционал в демо-профиль. |
| Р-K | Доступен ли чат в демо? | **Да, на демо-данных** (вариант а). | Демо-пользователь ходит во внешний LLM → нужны лимит запросов для демо (паттерн `ImportBotDailyUsage`) и учёт стоимости. Приватность демо-профиля не проблема — он синтетический. |
| Р-L | Что за «другой wow» в демо? | **Структура + сведение всех целей и идей в единую картину.** Агент поверх структуры, не вместо. Режиссура демо — отдельное исследование. | Чат не должен ломать/подменять этот wow. |
| Р-M | Данные во внешний LLM — ок? | **Ок, но с прозрачностью контекста** (вариант б): видно, какой срез ушёл в модель. Тумблер «сколько отдавать» — по желанию. | Дух WOLF «под контролем». Self-hosted для реального клиента — «бесплатно» через другой `wolf.llm.url`, отдельным решением не заводим. |
| Р-N | «Модель на выбор» — кто выбирает? | **Одна модель из конфига, задаёт админ, без выбора в UI** (вариант б). | Сознательно сужает исходную формулировку ради MVP. `wolf.llm.model` уже есть. |
| Р-O | История чата хранится? | **Да, переписка хранится между сессиями** (в MVP). | Нужна модель хранения (`ChatSession`/`ChatMessage` + миграция Flyway, последняя виденная `V17`); прошлые сообщения тоже контекст (влияет на Р-F). |
| Р-P | MVP-разрез принят? | **Да, целиком** (см. ниже). | — |

## Технические требования (выведены из решений)

- **Т-1 (из Р-D/E):** «подтверждение» в свободном чате должно быть **структурированным** — агент
  возвращает не только текст, но и машинно-читаемое «предлагаемое действие» (что создать/изменить/
  удалить, с полями), иначе кнопка «Подтвердить» не знает, что применять. Тот же приём, что в
  текущем парсере (кандидаты + `/import/confirm`), но внутри диалога.
- **Т-2 (из Р-H):** агрегаты динамики считаются кодом (переиспользовать `FactAggregateService`
  и др.), в LLM уходит уже посчитанный компактный текст/таблица.
- **Т-3 (из Р-O):** персистентная история — новая сущность(и) + миграция Flyway; учитывать в
  сборке контекста.
- **Т-4 (из Р-K):** лимит запросов для демо-аккаунтов (паттерн `ImportBotDailyUsage`).
- **Т-5 (из Р-C):** маршрутизация намерения (совет / создать / импортировать) — внутри одного
  агента; текущая логика `ImportParserService`/`ImportConfirmService` переиспользуется как
  «инструмент создания сущностей», а не как отдельная кнопка.

## MVP-разрез (Р-P — принят)

**В MVP:**
1. Кнопка «＋» открывает **диалоговый чат** (история сообщений), а не одноразовый парсер.
2. Один встроенный агент-планировщик, промпт от разработчика (Р-B).
3. Контекст: узкий срез (активные проекты, цели, рутины) + посчитанная кодом динамика
   расписания (Р-G/H), дотягивание глубже по ходу (Р-F).
4. Агент советует **и** предлагает действия (создать/изменить/удалить Записи времени, Дела …)
   — всё через подтверждение (Р-D/E) с машинно-читаемым действием (Т-1).
5. Модель из конфига (Р-N); прозрачность отданного контекста (Р-M).
6. Доступен залогиненному пользователю и демо-аккаунту, с лимитом для демо (Р-K).
7. Переписка хранится между сессиями (Р-O).

**НЕ в MVP (осознанно потом):**
- Пользовательский конструктор агентов / свои промпты (Р-B).
- Несколько агентов как отдельные сущности в UI — импорт внутри того же окна (Р-C).
- Выбор модели в UI (О-2).
- Голосовой ввод в чат (`transcribe` есть, но отдельно).
- Режиссура демо-wow (О-1).

## Открытые пункты (вне этой прожарки)

- **О-1:** демо-сценарий и его wow — **отдельное исследование/брейншторм**, не в объёме этого
  направления.
- **О-2:** выбор модели в UI — отложен; исходная «модель на выбор» сужена до конфига (Р-N).

## Существующий фундамент (разведано по коду)

- LLM-транспорт готов: OpenAI-совместимый `/chat/completions`
  (`HttpImportParserLlmAdapter`), провайдер/ключ/модель через `wolf.llm.*`
  (`application.yml:33-38`, дефолт xAI Grok, флаг `wolf.llm.enabled`).
- Порт `AssistantPort` узкий (`transcribe`/`summarize`/`suggest`) — под чат расширять или
  заводить новый порт.
- Данные контекста уже собираются частями: `morning-digest`, `ResumeResponse` (сводка проекта),
  `time-entries` (расписание), `goals`, `FactAggregateService` (агрегаты факта).
- Текущая кнопка «＋» = одноразовый парсер (`ImportChatPanel.vue` + `ImportParserService` +
  `ImportConfirmService`) — эволюционирует в диалоговый чат; логика создания сущностей
  переиспользуется как инструмент агента (Т-5).
- Баг Б-1 (тихий no-op парсера, релиз 1.3): при переходе к чату его судьба зависит от Т-5 —
  либо чинится в 1.3 параллельно, либо поглощается новой логикой подтверждения. Решить в spec.
