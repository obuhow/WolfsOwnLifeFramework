**Порядок (решение владельца), выведен из зависимостей:**


Включая новые поля модели: часы у Идеи и числовой вес у Синергии. Демо их только показывает.

## 2. Противоречия и решения владельца

### A. Прогноз Гантта — read-only производная от факта 🔴→ РЕШЕНО

`GanttForecastService.forecast()` берёт `weeklyAvg` **только** из факта прошлых 4 недель
(`recentFact / 4`, :97) и не принимает никакого входа. Ползунку «25 → 7 ч/нед» некуда писать.

Дополнительно: порог `MIN_WEEKLY_AVERAGE = 0.5` (:55) — при среднем ниже 0.5 ч/нед
`forecastEnd` остаётся `null`, то есть на левом краю ползунка Гантт **перестал бы рисовать
прогноз** вместо «плавного сдвига финиша на октябрь».

**Решение владельца:** ввести **what-if прогноз** — необязательный параметр
«предполагаемые часы в неделю», который подменяет `weeklyAvg` в существующей формуле.
Расчёт остаётся детерминированным (считает код, не LLM), ответ — та же дата финиша.
Пресеты 4 / 8 / 14 / 25 ч/нед выше порога 0.5, поэтому `null`-прогноз пользователю не
показывается. Формула переиспользуется в Ф3 (реш. E) — это одна механика на две фичи.

### B. «Подработка» и «расписание перестроено» vs модель 🔴→ РЕШЕНО

Заявка обещает: «Чтобы сбалансировать бюджет, подключаем 1 день подработки. Расписание
перестроено без драмы».

Что есть фактически:

- **денег в модели нет ни в каком виде** — grep по `api/src/main/java` не даёт ни дохода,
  ни ставки, ни подработки;
- `ResourceCascadeService` считает дефицит **часов** по Целям и явно фиксирует границу:
  «Бюджеты автоматически не меняются» (`ProjectDetailView.vue:558`);
- автоматического перестроения Записей времени не существует.

Это ровно тот случай, который прожарка 1.2 (реш. B) уже ловила: обещать гостю
функциональность, которой нет.

**Решение владельца:** **убрать оба обещания.** Показываем только честную физику — сдвиг
горизонта (реш. A) и дефицит часов по Целям, который `ResourceCascadeService` **уже умеет
считать**. Деньги в модель не заводятся; если понадобятся — это отдельный крупный релиз
вне 1.5–1.9.

### C. Ночной агент не работает на демо-госте 🔴→ РЕШЕНО

`AgentJob.runForAllUsers()` фильтрует `findByAccountTypeAndStatus("REGULAR", "ACTIVE")`
(:81) — аккаунты `DEMO` из ночного прогона **исключены**. Плюс `wolf.llm.enabled` по
умолчанию `false` (`NotesAssistantProperties`, `docker-compose.yml:44`).

Ключевая находка: фильтр `REGULAR` стоит **только** в `runForAllUsers()`;
`runForUser(user)` его не проверяет. Значит `POST /api/v1/admin/agent/run` для демо-гостя
работает уже сейчас, а ночной cron демо-аккаунты не трогает — LLM-квота в 4 утра на демо
не тратится.

**Решение владельца:** оставить это разделение как есть. Кнопка «Смоделировать ночь»
дёргает синхронный прогон для текущего пользователя; ночной cron по-прежнему только для
`REGULAR`. Для демо-стенда требуется `WOLF_LLM_ENABLED=true` — это условие эксплуатации,
фиксируется в тикете релиза 1.7.

### D. «3 карточки от агента» vs модель Note 🟡→ РЕШЕНО

Заявка обещает «🎬 подборка для разогрева (18 мин)», «💡 заметка-находка», «🎨 палитра/
референс». Фактически `Note` несёт `body` (TEXT) + `tags[]` (`Note.java:60-70`) — ни
типа, ни ссылки, ни длительности. Ни одного модуля видео/RSS/изображений в `api/src/main` нет.

**Решение владельца:** **тип карточки уходит в тег** (`разогрев` / `инсайт` / `референс`)
поверх существующего `agent-suggestion`. Новых сущностей не заводим, длительность и
внешние ссылки не обещаем. Утренний обход группирует карточки по тегу.
→ Это согласуется с реш. B прожарки 1.2, которое уже вырезало обещание «агенты читают
новости»: агент по-прежнему пишет текст по темам проекта.

### E. Синергия не умеет считать часы 🔴→ РЕШЕНО

`Synergy` = ручная тройка (`project`|`idea`|`routine`) × `sphere` × `impact ∈ {POSITIVE,
NEGATIVE, NEUTRAL}` (`Synergy.java:60-72`). **Ни одного числового поля.** У `Idea` —
`title`, `description`, `category`, `status`, `promotedProject` (`Idea.java`), ни часов,
ни сроков. Вердикты «−6 часов свободного времени», «−1 час сна», «сдвиг основного проекта
на 1,5 месяца» выводить не из чего. Плюс `impact` сегодня проставляет человек руками —
автооценки идеи нет.

**Решение владельца:** **числа появляются в модели** (Идея несёт оценку часов в неделю,
Синергия — числовой вес), но **заполняет их агент релиза 1.4 предложением, а пользователь
подтверждает**. После подтверждения считает код, детерминированно. Сдвиг срока основного
проекта **не считается заново** — переиспользуется what-if формула из Ф1 (реш. A):
идея отнимает N ч/нед → подставляем уменьшенные часы → получаем новую дату финиша.
→ Это соблюдает установку «действия LLM-агента — только через подтверждение».

### F. Воронка разогрева: нет стадий, нет таймера, панель скрыта 🟡→ РЕШЕНО

Три факта из кода:

1. `FocusSession` несёт только `user`, `delo`, `startedAt`, `endedAt`, `note`
   (`FocusSession.java:36-52`) — **поля стадии нет**; последняя миграция `V42`.
2. «Ступень 3: Поток — таймер отключается» — **отключать нечего**: таймера в WOLF нет
   вообще (grep по `web/src` и `api/src/main` даёт только `setTimeout`-дебаунс в
   `loadChartsWrite.js`). Фокус-сессия — это `startedAt`/`endedAt` + Отметки переключения.
   Мы не заменяем Pomodoro, а вводим **первую** механику стадий.
3. `FocusPanel` рендерится только при `timeCaptureMode === 'PRIMARY_FOCUS'`
   (`TodayView.vue:858`), а дефолт — `PARALLEL_SLOTS` (`User.java:76`). В режиме по
   умолчанию воронки не видно.

**Решение владельца:** **воронка работает в обоих Режимах фиксации времени** — выносим её
из `FocusPanel` на саму ячейку / Главное дело Ежедневника. Дефолт `PARALLEL_SLOTS` не
меняется, режим «Фокус» не становится обязательным. Текст третьей ступени
переформулируется: не «таймер отключается», а «система фиксирует фактические
15-минутные Записи времени».

### G. Переключение архетипа в шапке = уничтожение данных 🔴→ РЕШЕНО

Заявка: «При смене профиля в шапке все модули мгновенно синхронизируют контекст».
Единственный существующий механизм — `reloadProfile` → `userPurgeService.purgeProfileData(user)`
(`OnboardingService.java:163`), который **удаляет всё**: фокус-сессии, чек-листы, бэклог,
week-plans, рутины, синергию, заметки, идеи, цели, записи времени, дела, проекты
(`UserPurgeService.java:107-137`).

То есть «переключил архетип» = «стёр и пересоздал весь мир гостя». Настоящее переключение
контекста (три архетипа сосуществуют) — это либо три аккаунта, либо поле «активный
профиль» с фильтрацией каждого запроса, то есть сквозная переделка модели.

**Решение владельца:** **честный переключатель** — «начать заново как другой архетип» с
явным подтверждением потери данных, поверх существующего `reloadProfile`. Никакого
«мгновенно синхронизируют контекст» не обещаем. Сквозная переделка модели в 1.5–1.9
не входит.

Дополнительно: `worker-class` называется «**Рабочий класс**» (`worker-class.json`), а
заявка требует «**Инженер на разгоне**» с личным кейсом автора. Переименование +
наполнение историей — часть релиза 1.5.

### H. Пять нарушений визуального контракта сразу 🔴→ РЕШЕНО

Что действует **сейчас**: ADR-0007 пересмотрел контракт 0.3, но явно оставил в силе
«отсутствие теней, отсутствие синего акцента, зелёный зарезервирован за фактом,
**отсутствие прогресс-баров/процентов**». Спека 0.3 прямо проектирует наш случай:

- история 37: «Life Spheres and Synergy show positive, neutral and negative impacts
  **with signed typography and labels rather than alarming colour semantics**» — радар
  синергии уже спроектирован **без** ⚠️ и красного;
- история 16: план vs факт «**without a red/green judgement system**»;
- история 41: без стриков и «red absence markers»;
- ADR-0008 отдельно оговаривает: исключение «**не создаёт прецедента** "эмодзи разрешены в WOLF"».

Заявка требует: 🌙☀️🎬💡🎨 вне тура; **намеренные красные алерты** («кнопка-сравнение с
Jira/Todoist»); ⚠️ «удар по сфере»; радар как графику; гашение экрана и эмбиент-звук
(звука в WOLF нет вовсе, а `--wolf-transition` при `prefers-reduced-motion` = `0s`,
`tokens.css:112`).

**Решение владельца:** **контракт держим.** Wow делается типографикой и числами, как уже
спроектировано историей 37. Конкретно:

- **🐺 остаётся** (действующее исключение ADR-0008), **прочие эмодзи не используются** —
  ни 🌙, ни ☀️, ни 🎬/💡/🎨;
- красных алертов нет **даже как антипримера**: блок «сравнение с обычными трекерами» в
  таком виде не делается;
- ⚠️ заменяется знаковой типографикой (`+` / `−`), как предписывает история 37;
- эмбиент-звука и гашения экрана нет; переход «ночь → утро» решается сменой состояния
  экрана, а не анимацией и звуком.

→ **Нового ADR не требуется**: решение ничего не меняет в контракте, а подтверждает его.
ADR-0006, 0007, 0008 остаются в силе без правок.

### I. Два тура в одном меню 🟡→ РЕШЕНО

`onboardingSteps.js` — 14 шагов с 🐺 (19 вхождений), движок `OnboardingTour.vue` ждёт
**успешного ответа API** на каждом шаге создания. Заявка добавляет вторую кнопку
«90-Сек Wow Тур» в шапку.

Разбор показал: 90-секундный сценарий на **пустом реальном** аккаунте вырождается —
0–15 сек выбор архетипа (у реального пользователя архетипа нет), 15–35 ночной агент
(нет проектов → `AgentJob` нечего обрабатывать), 35–60 ползунок (нечего пересчитывать),
60–80 синергия (нет истории). Тогда как 15-шаговый тур ведёт **по настоящему аккаунту**
(`OnboardingTour.vue:86`) и учит создавать Проект/Дело/Запись/Рутину.

**Решение владельца:** **Приветственный тур остаётся** и включается вручную (он уже
`kind:'action'` в NAV, `App.vue:94`) — обучение заполнению по требованию. Для демо
делается **новая механика** 90-секундного показа. Тур из релиза 1.2 не архивируется,
ADR-0008 остаётся в силе.

## 4. Изменения глоссария (внесены в CONTEXT.md)

1. **+ «Прогноз по факту (what-if)»** — новый термин: сдвиг горизонта проекта при
   заданном темпе часов в неделю; детерминированный расчёт поверх `GanttForecastService`.
2. **+ «Ночной агент»** — новый термин: фоновый прогон `AgentJob`, оставляющий
   заметки-подсказки автора `Агент`; ночной cron только для `REGULAR`, ручной прогон —
   для текущего пользователя.
3. **+ «Воронка разогрева»** — новый термин: три ступени входа в работу (лёгкий контакт →
   разбор подсказки → поток); работает в обоих Режимах фиксации времени, таймера не вводит.
4. **+ «Архетип демо-профиля»** — новый термин: демо-профиль с готовой историей;
   переключение = повторная загрузка профиля с потерей данных.
5. **Δ «Синергия»** — уточнение: несёт числовой вес; оценку предлагает агент, подтверждает
   пользователь, считает код.

## 5. Флаги ADR

- **Нового ADR не требуется.** Решение H подтверждает контракт 0.3 + ADR-0007, а не
  отклоняется от него; ADR-0006/0007/0008 остаются в силе без правок.
- **ADR-0008 не отменяется** (реш. I): Приветственный тур сохраняется, 🐺 и счётчик шагов
  внутри его оверлея остаются законными.
