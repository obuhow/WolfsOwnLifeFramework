> ⚠️ **Расширение контура агента относительно решения владельца B релиза 1.2.**
> В 1.2 контур агента сознательно сведён к заметкам-подсказкам
> (`.scratch/release-1.2-onboarding-tour/spec.md:57`, `grill.md` §2 реш. B). Данный тикет
> даёт агенту право писать в расписание (создавать Записи времени). Это **новая возможность**,
> а не восстановление регрессии — до слияния нужна явная приёмка владельца. Фиксируется в
> `## Answer` и в `spec.md` релиза 1.3.

## Вопрос

Сделать так, чтобы запрос встроенному агенту на вставку Дел в расписание давал видимый
результат: агент **создаёт запланированные Записи времени** для Дел, у которых задано
«Правило повторения», и пользователь получает отклик (сколько создано / пропущено). Плюс —
точка входа в UI, чтобы запуск вообще был доступен и возвращал ответ.

## Доказательство контекста

- **Агент сейчас не пишет расписание:** `agent/AgentJob.java:121-128` сохраняет только
  `Note(author=AGENT, tag=agent-suggestion)`; `timeEntryRepository` используется только на
  чтение (`:147`, `findOverlapping` в `isActive`). Ответ `AgentRunResponse` не несёт полей
  расписания (`agent/dto/AgentRunResponse.java:22`).
- **Материализация уже реализована в отдельной фиче:** `recurrence/RecurrenceService.java`
  — единственное место с `timeEntryRepository.save(... status=PLANNED)` (`:104-110`).
  Публичная поверхность, пригодная для переиспользования агентом:
  - `ApplyResult apply(User user, Long deloId, ApplyCommand command)` (`:60`) —
    транзакционно раскладывает слоты Дела по горизонту, пропускает прошедшие/занятые;
  - `List<Slot> slotsOf(Delo delo)` (`:158`) — достаёт сохранённое «Правило повторения»;
  - `ApplyCommand(weekdays, windowStart, windowEnd, horizonWeeks, slots)` — если `slots`
    пуст, `resolveSlots` (`:172`) сам берёт правило из Дела через `slotsOf`.
- **Нет точки входа в UI:** эндпоинт `POST /api/v1/admin/agent/run` (`AgentController.java:29,35`)
  admin-scoped; `grep -rn "admin/agent\|agent/run" web/src` → пусто. Штатный запуск —
  `@Scheduled` cron (`AgentJob.java:72`).
- **Глоссарий:** «Правило повторения» — «при применении создаёт будущие Записи времени на
  ограниченный горизонт» (`CONTEXT.md:79-81`); «Запись времени» — статус «запланирована»
  для плана (`CONTEXT.md:11-13`). Целевое поведение полностью укладывается в модель — менять
  её не нужно.

## Что сделать

1. **Агент раскладывает расписание через `RecurrenceService`.** В `AgentJob` для активных
   Дел пользователя, у которых задано «Правило повторения» (`slotsOf(delo)` непустой),
   вызвать `recurrenceService.apply(user, delo.getId(), new ApplyCommand(null,null,null,
   horizon, List.of()))` — команда без слотов заставит сервис взять правило из Дела.
   Дела без правила агент **не трогает** (не выдумывает слоты — детерминизм, не LLM).
2. **Идемпотентность.** `RecurrenceService.apply` уже пропускает занятые (`skippedOccupied`)
   и прошедшие (`skippedPast`) ячейки — повторный прогон агента не плодит дубли на уже
   занятых слотах. Проверить это тестом (повторный `run` → второй раз `created=0`).
3. **Ответ агента с числами расписания.** Расширить `AgentJob.AgentRunResult` и
   `AgentRunResponse` полями `timeEntriesCreated` (и, по желанию, `skippedOccupied`,
   `skippedPast`), просуммированными по Делам. Существующие поля
   `projectsProcessed/notesCreated/runsLogged` сохранить (обратная совместимость ответа).
4. **Точка входа и отклик в UI.** Добавить пользователю доступный способ запустить агента и
   увидеть результат. Способ реализации выбрать при работе, обосновать в `## Answer`:
   - вариант A: кнопка «Запустить агента» на подходящем экране (напр. Утренний обход /
     Настройки) → вызов эндпоинта → нейтральное сообщение «Создано N запланированных Записей
     времени; заметок-подсказок: M» (оформление по контракту 0.3 — без красного/тревожного).
   - вариант B: пользовательский (не admin) эндпоинт запуска «для себя» + кнопка. Если текущий
     `admin/agent/run` останется единственным, кнопку показывать только роли ADMIN и это явно
     отметить (тогда обычный пользователь по-прежнему без ручного запуска — зафиксировать как
     ограничение).
   Показ ошибки при неуспехе обязателен — «совсем ничего» (симптом Б-1) недопустимо.
5. **Горизонт.** Использовать существующие границы `RecurrenceService` (1..12 недель,
   `MIN/MAX_HORIZON_WEEKS`, дефолт 4). Значение горизонта для агентского прогона задать
   константой/настройкой и отметить в `## Answer`.

## Testing Decisions

- **Материализация:** у Дела задано правило (напр. вторник 20:00–21:00, горизонт 4 недели);
  прогон агента → в `GET /api/v1/time-entries` появляются 4 запланированные Записи времени по
  вторникам; `AgentRunResponse.timeEntriesCreated == 4`.
- **Дело без правила** агент не трогает — Записи времени по нему не создаются.
- **Идемпотентность:** второй прогон подряд → `timeEntriesCreated == 0`, дублей нет
  (всё уходит в `skippedOccupied`).
- **Прошедшие слоты** внутри горизонта пропускаются (`skippedPast`), а не создаются в прошлом.
- **Обратная совместимость ответа:** старые поля `projectsProcessed/notesCreated/runsLogged`
  присутствуют; заметки-подсказки продолжают создаваться как раньше.
- **UI:** запуск из интерфейса возвращает видимое сообщение с числом созданных Записей;
  при ошибке показывается ошибка (не тишина). Оформление нейтральное (контракт 0.3).
- **Бэкенд-регресс:** `AgentApiIT` зелёный (расширить на новое поле ответа и на материализацию);
  `npm run build` зелёный.

## Out of Scope

- LLM-генерация «оптимальной» раскладки — используем детерминированное «Правило повторения».
- Новостной дайджест / советник по энергии (реш. B 1.2 — остаётся вне контура).
- Изменение модели Записи времени (одна ячейка = одна Запись сохраняется).
- Автоматический ежедневный cron-прогон менять не требуется — тикет добавляет ручной путь и
  материализацию; поведение `@Scheduled` остаётся, но теперь тоже начнёт писать расписание
  (это следствие п.1 — отметить в `## Answer`, чтобы не стало сюрпризом).
