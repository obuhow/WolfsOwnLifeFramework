## Problem Statement

Релиз 1.3 — «укладка» техдолга: закрываем дефекты, накопленные к 1.2, начиная с
поведения **встроенного агента**. Это не функциональный релиз-прирост, а доведение уже
существующих механизмов до ожидаемого поведения.

Первый и порождающий пункт релиза — **Б-1**: при отправке запроса встроенному агенту на
вставку Дел в расписание ничего не происходит — ни сообщения об успехе, ни ошибки,
расписание остаётся пустым. Разбор показал, что это не сбой, а совпадение двух дыр:

- агент по коду **не умеет** создавать Записи времени — он только оставляет заметки-подсказки;
- в веб-интерфейсе **нет точки входа** для запуска агента (эндпоинт только серверный,
  admin-scoped), поэтому пользователь буквально не получает никакого отклика.

## Важное расхождение с ранее принятым решением (требует приёмки владельца)

Целевое поведение «агент сам раскладывает Дела по расписанию (создаёт Записи времени)»
**расширяет контур агента за пределы решения владельца B релиза 1.2**:

> grill 1.2, реш. B: «"AI читает новости", "ИИ посоветует снизить нагрузку" — в коде нет →
> переписать шаги по факту: **агент оставляет заметки-подсказки** по темам проекта… Новые
> фичи в 1.2 не входят.»
> (`.scratch/release-1.2-onboarding-tour/spec.md:57`, `grill.md` §2 реш. B)

То есть в 1.2 контур агента был сознательно сведён к заметкам-подсказкам, а материализация
расписания оставлена ручному «Правилу повторения» (`RecurrenceService`). Тикет 01 релиза 1.3
разворачивает это решение: агент получает право писать в расписание. Это **новая
возможность агента**, а не восстановление регрессии — поэтому релиз 1.3 требует явной
приёмки владельца по объёму контура агента до слияния тикета 01 (по правилу «молча менять
зафиксированное решение нельзя»). Решение владельца фиксируется здесь и в `## Answer` тикета 01.

## Out of Scope

- Новостной дайджест / чтение внешних источников агентом (остаётся вне контура, реш. B 1.2).
- Советник по энергии на основе рутин сна (реш. B 1.2).
- LLM-планирование «оптимальной» раскладки — тикет 01 использует детерминированное
  «Правило повторения» Дела (`RecurrenceService`), а не генеративную модель.
- Изменение модели Записи времени (одна ячейка = одна Запись) — материализация идёт
  существующим контрактом `RecurrenceService`.
